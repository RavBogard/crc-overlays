# MCP gap analysis: overlays, services, live control and Companion

Date: 2026-09-23. Read-only audit of the `crc-overlays-vercel` checkout (release `ebd4be4`) plus read-only calls against the live CRC MCP. Four audits ran in parallel (MCP surface, layouts/renderer, Companion, live/services/access); this file is the synthesis. File and line references were read directly; statements marked *(inferred)* were reasoned, not run.

## The goal and the rulings it is measured against

Daniel's goal: the MCP should make creating, modifying, pulling and retiring overlays simple and quick, with no significant coding and no novel workarounds, and the same for Companion presets, pages and buttons.

Rulings from the alignment rounds (2026-09-23):

1. Users are any editor at both congregations. Tools must be workspace-aware, safe and self-explaining.
2. Live control belongs in the MCP, fenced by a separate OAuth scope (`crc.live`) granted to Operator/Admin members at consent. Every live call names its target and is cue-logged with the agent as the source.
3. Publish end-to-end on a server fit pass plus a server-rendered image, with a post-hoc review list and rollback.
4. Layouts become data: a new layout like Corner should be definable through the MCP with no release.
5. Companion: both a stored per-workspace deck model (the whole deck, including camera, vMix and X32 buttons against existing connection IDs, exported as an importable config) and richer module presets. TBI gets its own deck.
6. Prepared services get full edit through the MCP, including generating a Companion service page. Catalog hygiene batch tools are wanted. Assets and branding are lower priority but included.
7. Headline acceptance test: centralreform.live setlist → prepared overlay service → missing graphics authored → Companion page for that week, in a handful of calls.

## Where things stand, in one paragraph

The authoring MCP is solid underneath: 29 tools with strict schemas, optimistic versions, a real server-side Chromium fit check that can already return a JPEG to the agent (`fit_check_draft{includePreviewImage:true}`, lib/server-fit.ts:38-40, 550-558), and custom text is already authorable (the corner "Thank you" was made over MCP). What makes it slow is ceremony and blind spots, not missing foundations. Publishing takes five calls with `previewId` threaded through three of them; a name collision at publish can't be confirmed and costs about five more; the agent can't tell which congregation it's connected to; about a dozen operations the web already uses aren't registered; layouts are a closed enum repeated in ten files; nothing about services beyond the initial import, nothing about live output, and nothing about Companion is reachable at all. The Companion deck is generated by a script that depends on Michael's raw export and hardcodes its structure, so every deck change is a code change.

## 1. Cross-cutting: identity and self-explanation

**Current.** The server name is hardcoded "CRC Overlay Authoring" (lib/mcp.ts:48) and tool descriptions say "CRC source corpus", on TBI too. The consent page says "Connect CRC authoring" on TBI (lib/oauth-http.ts:36). `get_workspace` exists in lib/authoring.ts but isn't registered. Each deployment has its own database, OAuth issuer and relay, so a token can only ever reach one congregation, but an editor at both shuls holds two connectors with identical names and identical tools, and the agent can't tell them apart from any output. The server sends no `instructions` field, so the workflow and house rules (corner uses a bottom template; more than two lower thirds becomes a left sequence; don't split long prayers with `split_draft_into_set`) live nowhere an agent reads. docs/MCP.md is out of date in two places: it says `review_draft` is absent (it's registered, mcp.ts:80) and that MCP accepts no arbitrary text (custom mode takes up to 4,000 characters, mcp.ts:18).

**Gap.** The single cheapest thing that serves "any editor, both shuls" is missing: the connection doesn't say who it is or how to use it.

**R-F1 (S).** Workspace-derived server name, consent copy and tool descriptions from `getPublicWorkspace()`; register `get_workspace`; echo `{workspaceId, shortName, host}` in every result; write a server `instructions` string carrying the workflow and layout rules; fix docs/MCP.md. Files: lib/mcp.ts, lib/oauth-http.ts, lib/workspace.ts, docs/MCP.md, tests/mcp.test.ts.

**R-F2 (S).** Every write and live tool takes a required `workspace` argument checked against `WORKSPACE_ID`, refused in plain words on mismatch. This is the guard against an agent holding both connectors and using the wrong one.

## 2. Authoring overlays

**Current, verified.** From nothing to a published custom graphic is five calls (create → preview → fit_check → review → publish). A source-backed graphic is about eight (search_sources, get_source for block IDs, list_templates, then the five). `review_draft` for an MCP actor only issues a receipt on a stored `server-chromium/` pass, and `humanApproved: z.literal(true)` is an assertion the agent makes on its own behalf; the receipt doesn't record that an agent approved. `publish_draft` has no `confirmDuplicateName` though the service supports it (authoring.ts:544-560), so "Publish anyway as X?" is a dead end that forces rename → full re-gate.

**Operations that exist in the service or web but aren't MCP tools:** `list_catalog` (baseline plus published cues; `list_drafts` hides never-imported catalog cues), standalone `duplicate_draft`, `preview_content` / `preview_baseline_cue` (look without writing a draft), `source_facets` / `list_book_units` and the `book`/`service` filters on search, the whole shared library (`list_shared_library`, `preview_shared_cue`, `customize_shared_cue`, `customize_shared_set`, `compare_shared_cue`, the CRC↔TBI bridge), `save_slots` (weekly names/guest text), source review (`scan/list/get/decide`), asset upload/list/archive, bulk publish, the custom-template composer (Speaker, Announcement, Scripture citation, Service begins, Corner card), and named text-size presets (the agent must know 42/35/34 vs 34/28/28).

**Ergonomics observed in live calls.** Compact `list_drafts` sorts by UUID (so "2 of 3" came before "1 of 3"), carries no set id/index/count and no "has unpublished changes" flag, and shows no text for custom drafts. Without `compact` or a filter it returns every draft in full with snapshots. `search_sources` with limit 2 returned about 6 KB, mostly licence blocks, and no block IDs. `get_draft` on a two-block panel was about 9 KB and still doesn't say what the graphic reads; learning that means `preview_draft`, which writes a record. Template names leak prayer names into layout choice (Shiru panels use template "Mourners Kaddish 1"; corner Thank You uses "Oseh Shalom"), and the template only contributes motion and duration.

**Custom content is one channel.** Custom text is a single `textMain` string; there's no structured Hebrew/transliteration/translation for non-liturgical graphics, no rows on panels, and custom drafts can't be split or be a variant base.

**Recommendations.**

**R-A1 (M). One-call publish.** `ship_draft{draftId, expectedVersion, allowRename?}` runs preview → fit with image → attested review → publish server-side and returns the image, verdict, revision and final name; on a fit failure it stops with the renderer's own sentences. Receipts record `approvedBy: agent|person` and the member. Replace the `humanApproved` literal. Add `confirmDuplicateName` to `publish_draft` regardless. Fragile: the 60 s `maxDuration` with a cold Chromium start and the 25 s fit deadline leaves thin margin; one graphic per call.

**R-A2 (M). Post-hoc review list.** Store the fit JPEG against the preview record; add `list_recent_publications{since, actor?}` and a web review page that shows what the agent saw, with a one-click rollback. This is the stated condition for ruling 3.

**R-A3 (M–L). Real retire.** `published()` honours `archivedAt`, so `/api/catalog` (Companion's picker) and the relay stop serving retired cues; add `retire_cue` / `unpublish`. Closes GAP-LOG item E. Fragile: relay behaviour when a cue it holds disappears is unverified; needs a relay test first. A first publish has no earlier revision, so retire is the only true retraction.

**R-A4 (S–M). Register the missing operations.** `list_catalog`, `duplicate_draft`, `preview_content` (with optional image), `list_book_units` plus search filters, the shared-library five, `save_slots`, source review. The operations exist; this is mostly schemas in lib/mcp.ts.

**R-A5 (S). Leaner reads.** Compact by default; rows carry `setId/setIndex/setCount`, `dirty`, `archived`, a text excerpt (custom included); sort by name then set index; `get_draft{view:'rendered'}` returns the on-screen texts without snapshots; search results drop the licence blob and can include block IDs. Keep the full-record path for audits.

**R-A6 (S–M). Looks, not template cues.** `templateCueId` becomes optional and defaults to the layout's look tile (`templateLooks()`); `list_templates` returns looks by layout; `list_custom_templates` / `compose_custom_draft{templateId, values}` on lib/custom-templates.ts; named text-size presets.

**R-A7 (M). Structured custom content.** Custom mode gains optional `he`/`tr`/`en` lines or rows so announcements and responses get proper bilingual lower thirds and panels. Fragile: slots and `publishSlotText` assume `mode:'custom'` with `text`.

## 3. Catalog hygiene

**Current.** Flags exist for shared accent titles, small fonts and alternating grouping; sets can be archived, restored and reordered; bulk publish is web-only. The four "Copy of Thank you" duplicates and the Zochreinu draft carrying "Mi Chamocha" as its on-screen title were found by hand. A rename of a published graphic costs a full re-gate because the name is part of the cue hash.

**R-H1 (M).** `find_catalog_issues`: duplicate `cueHash` or content, inherited titles and accents, stale pins, small fonts, archived-but-published cues, drafts with unpublished changes.

**R-H2 (M).** `batch_update` for style, rename or archive across N drafts, dry-run by default, per-item results, no stop at first failure (the bulk-publish pattern), and `batch_ship` that calls R-A1 per item with a resumable cursor rather than one long call.

**R-H3 (M, after R-A3).** `supersede_cue{old, new}`: repoints service entries and deck bindings to the new cue and retires the old one.

## 4. Layouts as data

**Current, with Corner as the worked example.** A layout is a string on the cue that becomes a CSS class (lib/player.ts:75). Geometry is absolute-pixel CSS in app/overlay.css, where the lower-third and panel rules are layered and "order is load-bearing" (lines 6-8); Corner is the only self-contained block (252-277). Each layout has its own fit routine with hardcoded budgets and floors (player.ts:35-49) dispatched by an if-chain (80). Motion is copied from a baseline catalog cue (authoring-model.ts:363-407), which ties it to the TBI catalog map. The layout name is a closed union or enum in about ten places. Corner touched roughly twelve source files, CSS, three or four test files, the Companion preset tests, docs, and a paired release, and it deliberately avoided adding a corner baseline cue because that would have changed both catalogs, the TBI map and the presets.

Two properties matter beyond cost. First, geometry isn't pinned: a published cue stores texts and motion, but its geometry comes from whatever CSS is deployed, so any CSS release silently changes every published cue of that layout. Second, `findFitErrors` is mostly generic already (frame, container, overflow, overlap), and the server fit check renders whatever the Player can render, so fit is the strongest foundation for data layouts. The layout-specific parts are the container selector (app/author/preview.ts:79), the lower-third 360 px ceiling, and `panelFillRatio`'s hardcoded denominators (which return null for corner, so corner never gets the sparse warning).

**Branding and assets, current.** Branding is three colours plus a logo path from env or code profiles; changing it is a redeploy. Several colours are hardcoded in CSS and never reach branding (paper, ink, accent-title `#8fe7e2`, translation ink, and the medallion ring, which is CRC gold on TBI too *(inferred on screen)*). Fonts aren't branding at all; TBI's requested Raleway isn't implemented. Assets have a proper table and upload route (PNG/JPEG/WebP, ≤512 KB, content-addressed), and drafts accept `imageAssetId`, but an agent can't upload or list assets, and the server fit check can't load artwork because the preview route requires author auth, so fit images never show custom art.

**Proposed model.** A small primitive kit stays in code: region primitives (card surface with optional title strip and accent rule, emblem, title lane with accent lane, text body), three arrangement renderers generalised from today's code (`columns` for lower thirds, `stack` for panels and corner, `rows` for panel rows), three fit strategies (`shrink-to-floor`, `grow-shrink-budget`, `measured-grow`), the motion vocabulary with named presets, a font registry, and validators. Everything else is a per-workspace, versioned layout definition document: frame (anchor, insets, width, height mode), surface, title and accent lane, body channels with logical direction and alignment (`start`/`end`, which removes the RTL `flex-end` bug class fixed this week), fit policy and budgets, capabilities (sets, translation, row order, block limit, character budget), motion preset and origin, and what it occludes (scan card, resting logo). The Player applies it as inline CSS custom properties on the box; one flat generic CSS block reads them. Stored in the database, not content/, because anything in content/ is owed a paired release. Published cues pin `layoutRef{id, version, sha256}` inside `cueHash`; editing a layout makes version N+1 and published cues stay on N until republished or rebased with a fit pass each.

**Recommendations, in dependency order.**

**R-L1 (S–M). Layout registry.** One module (lib/layout-registry.ts) with id, label, template motion, capabilities, thumbnail and fit hooks; replace the unions in layout-label.ts, template-looks.ts, panel-budget.ts, custom-templates.ts, authoring-model.ts (:11, :261, :369), authoring.ts (:118, :369, :385, :446), mcp.ts (:20, :53, :66, :70), app/author/types.ts, and preview.ts:79 (use a `data-contain` attribute). Pays off before any table exists. Fragile: MCP schema change must stay compatible with connected clients.

**R-L2 (M). Card primitive and parameterised fit, Corner first.** Generalise overlay.css:252-277 and `fitCornerText` into variables; golden-still test proves Corner pixel-identical before and after. The CSS-regex assertions in tests/corner-layout.test.ts will need rewriting.

**R-L3 (L). `layout_definitions` table, versioning and pinning.** db/, `buildCue`/`cueHash`, catalog and relay payloads, output page, player. Fragile: payload size and compatibility with older output pages still open in a browser source.

**R-L4 (M). MCP layout tools.** `list_layouts`, `get_layout`, `create_layout` (clone from an existing one), `update_layout` (draft status only), `validate_layout` (static: inside frame, no channel overlap, floor ≥ 20, id matches Companion's `/^[a-z][a-z0-9_-]{0,39}$/`, registered fonts), `preview_layout` (sample texts plus named drafts through the server fit, returns images), `publish_layout` (requires a passing sample set), `rebase_to_layout` (dry run by default).

**R-L5 (M). Motion as data.** The definition carries a motion preset or tracks; `buildCue` stops cloning baseline template cues. Removes the TBI catalog-map coupling for new layouts.

**R-L6 (S–M). Generalise the fit contract.** Container, fill denominator, sparse threshold and height ceiling come from the definition; server-side set budgets read capabilities.

**R-L7 (S). Font registry as code.** Generates the @font-face list, the `waitForOverlayFonts` targets and the TBI staged-asset allowlist (the Arabic 404 in release f753093 is the failure this prevents). A new face stays a release; uploaded fonts are deferred.

**R-L8 (L, last or never).** Migrate the existing lower third and panels into definitions only after golden stills prove equivalence. Until then they stay built-in kinds and new layouts use the card primitive. This is the fragile part: it's the live broadcast renderer, and gap H (`.right .prayer` placing text outside the panel) shows how brittle the layered rules are.

**R-B1 (M). Asset tools.** Chunked base64 `upload_asset` (begin/append/commit, ≤512 KB), `list_assets`, `archive_asset`, and a signed short-lived URL so the server fit can load artwork.

**R-B2 (M). Branding as data.** A versioned `workspace_branding` row: full colour set (including paper, ink, accent title, ring, translation ink), font roles chosen from the registry, logo, resting-logo and scan-card artwork as asset ids; hardcoded CSS colours become variables; `get_branding` / `update_branding` with a preview across representative cues.

## 5. Prepared services

**Current.** The web can create, import, add/move/remove entries and coverage rows (by whole-array replace), set and clear names lists (refused while a names panel is on air), archive and restore, and record feedback. The MCP has only `prepare_service_from_setlist` and `get_service_history`.

**Structural gaps that block full edit and page generation (verified).** Coverage rows aren't linked to entries; the importer creates an alternates entry and a needs-review row that share only a label, candidate cue ids live only in the `reason` prose, and rows without a graphic get no entry, so setlist order for them is lost. No provenance is stored (setlist id, track ids, event date), so there's no re-import, no reliable "this week's service", and no reconciliation with centralreform.live. There are no panel-set, button-label or camera fields. `serviceRef` is never sent by console or Companion, so the cue log can't say which service a command belonged to.

**R-S1 (M–L). Service model.** One ordered `rows[]` (setlist position, coverage status, linked entry, candidate cue ids, button label, optional camera hint and note) plus `origin{setlistId, trackId per row, eventDate, importedAt}`; lazy migration on read. Fragile: these JSONB documents are live, and the parse functions keep prior unavailable ids.

**R-S2 (M). Services tools.** `list_services`, `get_service` (compact, not the whole dashboard), `list_live_setlists`, `create_service`, `rename_service`, `add_entry`, `remove_entry`, `reorder_entries`, `swap_graphic`, `resolve_coverage_row` (also rewrites the linked entry), `set_coverage_row`, `set_names` / `clear_names`, `archive_service` / `restore_service`, `refresh_from_setlist`, `service_readiness` (counts by status, unresolved rows with candidates).

**R-S3 (S, with the deck work).** Buttons generated from a service stamp `serviceRef` on their commands, so the cue log attributes them.

## 6. Live control

**Current, verified.** Console and Companion POST `/api/command`; the relay gives exactly-once receipts per `commandId`, per-controller sequence ordering, cue-conditional take-out and a source-aware cue log. The relay already accepts `source:'mcp'`, but no web path can send it. The response is HTTP 200 whether a command was applied, replayed or dropped as stale; there's no `accepted` flag and no precondition ("only if revision is N"). Next panel has no server action; Companion computes it from the "— NN of MM" naming convention. Clear now (`cut`) also removes the scan card and turns the resting-logo preference off. The resting logo state is a preference; nothing reports whether it's visible. The console already exposes browser-side WebMCP tools that send commands as `source:'control'`, so agent actions through that path are already indistinguishable in the log.

**Rehearsal vs live is not a real distinction on the server today.** Each workspace has one relay with one room (`ROOM='crc'`); "rehearsal mode" is a local, memory-only process that fails closed on Vercel. A `target:'rehearsal'` call today would either be refused or silently go live.

**Roles, a conflict to settle.** On the web, Editors can operate live today (`canAccess` gives `control` to every role; ACCESS.md says "Editor can author, publish, and operate"). The ruling "Operator/Admin only" for `crc.live` is stricter than the web.

**R-V1 (M). Shared live-command core.** Extract the route body into lib/live-command.ts so the route and MCP share validation, gating and the relay call; MCP sends `source:'mcp'`, a stable `clientId` from the token family, a clock-based sequence, and accepts a caller-chosen `commandId` so a retried tool call replays safely. The relay returns `outcome: applied|replayed|superseded` and stores `commandId` on history rows. Fragile: relay ships before web (docs/RELAY-RELEASE.md); a `commandId` in history needs a ruling against the log's "not surveillance" posture (it's a correlation id, not identity).

**R-V2 (M). `crc.live` scope.** Subset scopes in `normalizeScope` (keep existing `crc.authoring` rows valid), consent that grants the intersection of requested scopes and role with its own sentence and an unchecked-by-default box, scope-aware member re-check on every request and refresh, per-tool gating with `insufficient_scope` step-up. Fragile: whether Claude and ChatGPT actually step up is unverified *(inferred)*.

**R-V3 (M–L). Live tools.** `get_live_state` (requested, rendered acks, controllers seen, catalog sync, workspace), `show_graphic`, `take_out`, `animate_out`, `clear_now` (requires `immediate:true` and says what it also clears), server-side `next_panel` / `previous_panel` (port companion/src/panel.ts), `set_scan_card`, `set_resting_logo` (result says "preference on; hidden under any graphic"). Each takes required `workspace` and `target`, optional `commandId`, `serviceId`, `ifRevision`; each waits up to about 3 s for a matching renderer ack and reports rendered or not-acknowledged; each reports whether a Companion is attached. Fragile: racing Michael's Companion (last writer wins); a guard such as `confirmOverride` while a Companion was seen in the last 30 s is a policy call.

**R-V4 (S).** Console WebMCP commands tagged `source:'mcp'`.

**R-V5 (L). A real rehearsal room.** A second Durable Object room per relay with ticket room claims, a `room` field on command/state/history/catalog, catalog sync to both rooms, and a rehearsal output URL for a practice browser source. Until it exists, `target` accepts only `'live'`. Fragile: the `room:'crc'` literal is asserted in several places, and operators could confuse the two browser sources.

## 7. Companion

**Module, current (v1.7.0).** Actions: show/toggle/animate-out cue, animate clear, clear now, refresh catalog, scan card on/off/page, logo on/off/toggle, next/previous panel. Seven feedbacks, thirteen variables plus one per slot. Presets: one toggle preset per visible cue, one per slot, eleven utilities, all in one flat section. Catalog refresh is realtime (the README's "explicit only" claim is stale). Preset colour is by category (almost everything comes out teal) while the deck colours by role, so presets and deck disagree. Role and sequence data exist only in CUE-MANIFEST.json, not the catalog. No service data reaches the module. The installed base (2.0.4) already supports preset groups, so service and set sections are possible without a base upgrade. Module presets can only carry the module's own actions, so a preset can never contain a vMix merge, a PTZ recall or an X32 mute; the camera gesture can only reach the deck through an exported config. That's why the stored deck model is necessary, not just nicer.

**Deck generator, current.** scripts/build-companion-preset.mjs derives 439 bindings from CUE-MANIFEST.json and hardcodes the rest: the overlays connection id and module version, service chains (Fri 4–9, Sat 10–16, B'nai Mitzvah 17–18, HHD 19–25), 26 carried device pages, the palette and role colours, a button template cloned from the original export's page 76, the gesture recipe, the fixed columns (c0 switcher, c6 recovery, c7 nav with Bimah Mute), hand-placed Home/Output/Devices/Cameras pages, Singular translation tables, and the v12 envelope. It can't run without Michael's raw export, which supplies the button template, every device button, triggers and custom variables. Michael's grammar H1–H4 (column = slot, continuations down, lead at top, alternates share) is only implicit in hand-assigned manifest cells; nothing computes it. Each service page has 21 free cells and the manifest already peaks at 21. The audit's nine rules hardcode page ranges, a supersede regex list, the `'1.7.0'` literal, and rule 9 needs an 880 KB upgrade bundle that isn't in the repo.

**Import constraints, verified in the Companion 5.0.3 source clone.** Single-page import clears only the target page. Page references inside an imported page aren't remapped, so its jump targets must already be right for its slot. Connection mapping on page import pre-fills by label and module, and if no label matches it falls back to the first connection of the same module type; with five PTZ connections, one wrong label silently binds a camera gesture to the wrong camera. This is the fragile part of the whole Companion plan. Companion has no remote API that can import (driving its internal tRPC from a helper counts as driving it live, out of bounds). Uncertain: Michael's installed Companion and module versions and connection labels (OPEN-QUESTIONS Q3, Q4).

**R-C1 (L). Stored deck model and pure renderer.** Split the generator into lib/companion-deck/{model, render, seed}; a `companion_decks` table per workspace with optimistic version; model holds connections by role (seeded from export stubs), grid, palette and role colours, named page templates (service, hub, carried), sanitized device fragments (Bimah Mute, camera tally, carried pages, triggers, custom variables), pages with typed button specs (cue, jump, module action, fragment, camera merge), and named gesture recipes. A built-in layered button template replaces the page-76 clone. Acceptance: `renderDeck(seed)` reproduces today's preset byte for byte. Fragile: deterministic id seeds and carried device buttons that keep original page references.

**R-C2 (M). Model-driven validator.** The audit becomes lib/companion-deck/validate.ts reading chains, fixed cells and gesture shapes from the model; module definitions from a JSON manifest shipped with the module (instead of parsing main.ts); a new check that every connection label matches the registry exactly; rule 9 stays a CI check unless the MIT upgrade bundle is vendored.

**R-C3 (M–L). Deck tools.** `get_deck`, `get_deck_page`, `create_page`, `rename_page`, `move_page`, `delete_page`, `place_button`, `move_button`, `remove_button`, `bind_cue`, `attach_camera_gesture`, `apply_template`, `layout_column` (applies H2–H4 and role colours), `generate_service_page{serviceId, slot}` (entry → column, multipart stacks down and overflows right, alternates share a column, reuses the deck's existing gesture for a cue, chains nav and Home), `validate_deck`, `export_deck_config{scope: full|page}`, and a one-time `seed_deck_from_export` that strips config and secrets server-side.

**R-C4 (S–M). Export and delivery.** `app/api/companion/deck` serves full or single-page gzip with disabled connection stubs, via a signed short-lived URL returned by `export_deck_config` and listed on the setup page. The weekly page always lands in one fixed "This week" slot (a spare page such as 27) with a permanent Home jump, so importing it never disturbs other pages' navigation. Michael does a single-page import each week (Import/Export → page → slot → confirm mapping).

**R-C5 (M). Service-aware module presets.** `/api/catalog?include=services` carries the current prepared service in order plus role and sequence per cue (moved from CUE-MANIFEST into the catalog or deck model); the module gets "This week's service", "Sets" and "Controls" sections; one palette shared with the deck renderer. A `deck_version` variable can tell Michael a new page is ready. Keep new fields in the envelope so old clients still validate.

**R-C6 (S, before R-C5).** The TBI module derivation asserts exact counts of CRC strings in the compiled module (build-tbi-companion-module.mjs:198-202), so any new preset section breaks the TBI build. Move brand strings into one constant or read the product name from the catalog envelope.

**TBI: Simone's deck (export `TBIComputer_2026-09-14-1618`, read structurally; connection config and secrets were not printed).** She is already on Companion 5 (build 5.0.5, newer than Michael's 5.0.3), full v12 export, 99 pages on a 4×8 grid, but only 13 pages carry buttons: 1–6 and 8 for Shabbat and occasions, 95–99 for the High Holy Days. The deck has not been cut over: every graphic button fires Singular.live, across three Singular connections (`kab`, the Shabbat workspace, 132 compositions; `singular__HHDs`, 88; `morn`, configured but unused). There is no TBI Overlays connection in it. Devices are light: one BirdDog PTZ (a manual pan/tilt/zoom pad plus recall/save presets 1–4 on page 1) and OBS (two scene buttons on page 8). No switcher, no audio console, and no camera coupled to any graphic. Navigation is Companion's built-in page-up / page-number / page-down in column 0 of every page, which Michael's audit bans outright. Every graphic button is a two-step toggle (step 1 animate in, step 2 animate out), with no feedbacks, so nothing on her deck lights to show what's on air. Her grammar partly matches Michael's (numbered continuations run down a column: L'cha Dodi 1–4, Shalom Aleichem 1–4) but colour is per prayer, with no role rule. Labels carry her working notes ("NEED mi chamocha pt 2", "NEED 176 part 1"), many readings are named by Mishkan T'filah page ("Pg 149 Top", "157 middle pt 2"), and there are real defects a conversion must surface rather than copy. For example, "NEED mi chamocha pt 2" animates in "Sing the song 159" but animates out "Twilight People 2", so its second press doesn't clear what the first showed, and "V'ne-emar" fires Aleinu 2.

What this changes.
