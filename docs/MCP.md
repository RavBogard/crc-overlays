# Overlay authoring MCP

Each congregation's deployment hosts its own authoring endpoint at `/api/mcp` (CRC: `https://overlays.centralreform.org/api/mcp`). It uses the MCP TypeScript SDK's stateless Streamable HTTP handler, OAuth 2.1 authorization code flow with PKCE S256, and two resource scopes: `crc.authoring` and the opt-in `crc.live` (see "Scopes" below). It exposes source, draft, publish and prepared-service operations. The live-control tools need `crc.live` and are described under "Live control" below.

## Server configuration

Apply `db/oauth.sql` to the same PostgreSQL database as the renderer. Configure `PUBLIC_BASE_URL=https://overlays.centralreform.org`. No shared key takes part in consent: the person approving a connection is a signed-in workspace member (see "Consent" below), and `AUTHORING_KEY`/`CONTROL_KEY` are not read by the OAuth routes. Authorization codes, access tokens, and refresh tokens must never be logged. The database stores SHA-256 hashes of all opaque credentials.

Discovery endpoints:

- `/.well-known/oauth-protected-resource`
- `/.well-known/oauth-protected-resource/api/mcp`
- `/.well-known/oauth-authorization-server`

OAuth endpoints:

- `/oauth/register` for public-client dynamic registration
- `/oauth/authorize` for user consent and PKCE authorization
- `/oauth/token` for authorization-code and refresh-token grants
- `/oauth/revoke` for access-token revocation or refresh-family revocation

Authorization-server discovery advertises `crc.authoring`, `crc.live` and `offline_access` (optional refresh consent). The protected resource advertises `crc.authoring` and `crc.live`; `offline_access` grants no CRC data or permission of its own.

## Scopes

- A request may ask for any subset of `crc.authoring`, `crc.live` and `offline_access` that holds at least one of the first two. A request with no `scope` still means `crc.authoring`. Scopes are stored in one canonical order (`crc.authoring crc.live offline_access`), so every row written before `crc.live` existed (`crc.authoring`, `crc.authoring offline_access`) is unchanged and still validates; existing connections keep working without reconnecting.
- The grant is what was requested, intersected with what the person consented to and what their role allows. `crc.authoring` needs an Administrator or Editor. `crc.live` needs one of the explicit roles Administrator, Editor or Operator (`owner`/`editor`/`operator`), checked against that list rather than the web's `control` permission, so a role added later does not inherit live control. The token response's `scope` says what was granted.
- Every request and every refresh re-reads the approving member: a scope their role no longer allows stops at the next request (an Editor moved to Operator keeps live control and loses authoring), a refresh rotates to the narrowed scope, and a grant with no resource scope left is refused as an invalid token.
- The endpoint accepts a token holding either resource scope. Its 401 challenge still names `scope="crc.authoring"`, as before. Every tool is listed whatever the token holds; each tool group declares the scope it needs (`lib/mcp.ts`: the live group needs `crc.live`, every other group `crc.authoring`; `get_workspace` needs neither), and a call without it is refused before anything runs, in a sentence ending `(insufficient_scope: needs crc.live)`, for example "This CRC connection wasn’t granted live control, so show_graphic can’t run. Nothing was changed. To use it, reconnect the CRC connector and allow live control when you approve." Whether Claude or ChatGPT step up on that refusal is unverified.
- A connection's live commands go through the same core as `POST /api/command` (`lib/live-command.ts`) with `source:'mcp'`, one relay controller id per token family (stable across refreshes, derived from but never equal to the family hash) and a clock-based sequence. The caller's `commandId` is kept, so a retried call replays rather than pressing twice; `ifRevision`/`ifCue` pass through to the relay, and its `outcome`, `originalOutcome` and `lastPress` are read back (docs/RELAY-RELEASE.md).

Production redirect URIs must use HTTPS. HTTP is accepted only for loopback callbacks such as `http://127.0.0.1:49152/callback`. Registered redirect URIs must match exactly during authorization and code exchange. Authorization codes are one-use and expire after five minutes. Access tokens expire after one hour. Refresh tokens expire after 30 days and rotate on every use; reuse or revocation invalidates every refresh and access token in that family.

## Consent

The consent page at `/oauth/authorize` names the registered client and its verified return destination and offers **Approve** and **Deny**. Who approves is the workspace session — the same Google or password sign-in as the rest of the site — and that member must be an Administrator or an Editor for authoring (an Operator may approve live control only; see below). There is no key field.

The session cookie is `SameSite=Strict`, so the first arrival from an MCP client (a cross-site navigation from claude.ai or a desktop app) carries no session even when the person is signed in. Pressing Approve on that page is a same-site form post, which does carry it: a signed-in author is done in one click. Without a session the request is parked in a ten-minute `HttpOnly` cookie scoped to `/oauth/authorize` and the person is sent to `/access?next=/oauth/authorize`; after signing in, `/access` returns them to the consent page, which now reads "Approving as *Name* (*email*)", and Approve issues the code. An Operator sees "Your role here can’t author graphics. Ask an administrator for Editor access." A return with nothing pending reads "Sign-in didn’t complete. Start the connection again from your MCP client."

When the client asked for `crc.live`, the form carries one more line, a checkbox that is off until the person ticks it: "Live control: also let this connection show, take out and clear graphics on the CRC output, as the console does." It is offered only to the three live roles (before sign-in the role is unknown, and the post re-checks it). Unticked, the connection gets authoring only. An Operator can approve a live-only connection; an Operator approving a request for both without ticking the line reads "Your role here can’t author graphics, so this connection can have live control only. Tick Live control to allow it, or Deny." A live-only request approved without the tick reads "Nothing was chosen to allow. Tick Live control to connect, or Deny." A request for authoring alone shows the page exactly as before.

The code, the access token and the refresh token all carry the approving member as their actor (`mcp:<client>:member:<id>`). Every MCP request and every refresh re-checks that member: removing them from the workspace ends their MCP access at the next request, and moving them to Operator ends authoring (and live control stays only if it was granted). Tokens minted before this change, whose actor names no member, are refused; those clients reconnect through the new consent. The page stores only the opaque request handle in the form and the cookie, and never places a bearer token in a URL. Requests have durable database rate limits and bounded bodies.

## Which congregation (`get_workspace`)

Each deployment has its own database, OAuth issuer and relay, so a token reaches one congregation only. An editor at both congregations holds two connectors, so the connection says who it is everywhere an agent looks:

- The server name is `<short name> Overlay Authoring` (`CRC Overlay Authoring`, `TBI Overlay Authoring`), the consent page reads "Connect <short name> authoring", and tool descriptions name the congregation.
- `initialize` returns `instructions`: which congregation this is, the authoring workflow, and the layout house rules (corner takes a bottom template; text needing more than two lower thirds becomes a left panel sequence; use `create_source_draft_set`, not `split_draft_into_set`, for a long prayer in parts).
- `get_workspace` returns `{workspaceId, shortName, host, organizationName, rehearsal, rehearsalLabel}`.
- Every result starts with `{workspaceId, shortName, host}`.
- Every tool that changes anything takes a required `workspace` argument: the workspace id (`crc`, `temple-bnai-israel-kalamazoo`) or the short name. A call naming a different congregation is refused before anything runs: "This connection serves CRC (workspace 'crc' at overlays.centralreform.org), not '…'. Nothing was changed. Use the connector for '…', or pass workspace:'crc' if you meant CRC." Reads accept the same argument optionally and refuse a mismatch the same way.

## Authoring workflow

Clients can search licensed sources, inspect a source, list available cue templates, import an existing cue by ID, and create or update drafts. Source-backed content selects source and block IDs; bilingual drafts require identical ordered source/block coverage in Hebrew and transliteration. Content mode `custom` takes free text (up to 4,000 characters) for announcements and other graphics that come from no source.

The shortest source-backed path is two calls: `search_sources{query, includeBlocks:true}` returns each unit's block ids with their kind and first words, and `create_draft` takes those ids with no `templateCueId` (below). Neither `get_source` nor `list_templates` is needed when the defaults suit.

### Retire is not archive (packet A3)

- **Archive** (`archive_draft`, `archive_draft_set`) tidies the editor library. The published graphic keeps playing: it stays in `/api/catalog`, Companion's picker and the relay catalog.
- **Retire** (`retire_cue{cueId, expectedVersion}`) withdraws a published graphic from every live surface: `/api/catalog`, Companion's picker, the relay catalog, and the shared library shelf. The draft and its revisions are kept; the draft's active revision is cleared and the one that was live is remembered (`draft.retired`). A retired id also hides a built-in cue with the same id and any hidden alias that resolves to it. The editor lists it under Drafts as "Retired · out of the live library" with a Return action; `list_catalog` rows and `list_drafts` rows carry `retired`. Prepared services flag entries and coverage rows bound to it (`retired`, `cueRetired`), and a covered row reads needs-review. `isRetired(cueId)` in `lib/authoring.ts` is the check for deck validation.
- **Restore** (`restore_cue`) brings the remembered revision back with no new review. Publishing or rolling back a retired draft also brings it back; bulk publish skips retired drafts.
- **On air.** A graphic on screen when it is retired stays on screen (the relay holds its payload and a sync is not a command); its own Out still works, Clear and Cut still work, and it cannot be put up again. See docs/RELAY-RELEASE.md.
- A built-in graphic with no draft is refused with a sentence: import it (`import_cue`) first. A never-published draft is refused: archive it instead.

### Reads, looks and the editor's other operations (packet A1)

- **Leaner reads.** `list_drafts` is compact by default: rows sorted by name and then set order, each with `set {id, index, count}`, `published`, `dirty` (published, and the draft has changes the live graphic lacks), `archived`, and an `excerpt` of what it reads (custom text included). `includeArchived` adds archived drafts; `nextCursor` pages in name order. `compact:false` still returns every full record. `get_draft{view:'rendered'}` returns what the graphic reads on screen plus its version, set and publish state, without snapshots; the default view is the full record. `search_sources` is compact by default (no licence or pin blocks; `compact:false` restores the legacy summaries), takes `book`, `service` and (T2) `page` filters, and lists block ids with `includeBlocks:true`.
- **Looks.** `templateCueId` is optional on `create_draft`, `preview_content` and `create_source_draft_set`: left out, the layout's look tile (the one the editor offers first, `lib/template-looks.ts`) supplies it. `list_templates` adds `looks` (one per layout, with its template id and label; `mode` changes the labels) and `textSizes`. `textSize` (`comfortable`, `large` 42/35/34, `compact` 34/28/28) on `create_draft`, `update_draft`, `preview_content` and `compose_custom_draft` sets the three font sizes; explicit sizes in `presentation` win.
- **Custom forms.** `list_custom_templates` lists the speaker, announcement, scripture citation, service start and corner card forms with their fields; `compose_custom_draft{templateId, values}` makes the same unpublished custom-text draft the editor's form does. An unknown field or an overlong value is refused in a sentence naming the field.
- **Catalog and copies.** `list_catalog` lists baseline and published graphics, including ones nobody has opened (`query`, `layout` filters). `duplicate_draft{draftId|cueId, name?, expectedVersion?}` copies one into a new standalone draft.
- **Looking without a draft.** `preview_content` takes `create_draft`'s fields and stores nothing; `includePreviewImage:true` measures it in the server browser and returns the frame as an MCP image. That verdict is not stored and cannot stand in for `review_draft`.
- **Sources.** `list_source_facets` names the books and services; `list_book_units{book}` lists one book's printed outline (names and folios, never text).
- **Shared library.** `list_shared_library`, `preview_shared_cue` (copies the graphic's artwork here, so it is a write), `customize_shared_cue{expectedCueHash}`, `customize_shared_set{expectedCueHashes}` and `compare_shared_cue`, over the same shelf operations the editor uses.
- **Slots.** `list_slots{serviceType?}` returns each slot's graphic, text and draft version; `save_slots{serviceType, values, expectedVersions?}` is the "This service" Save: changed slots republish under their standing approval, and one overlong value or a stale `expectedVersions` entry refuses the whole Save before anything publishes.
- **Source changes.** `scan_source_changes`, `list_source_changes`, `get_source_change{id}` and `decide_source_change{id, expectedVersion, decision, reason?}` are the `/api/source-review` inbox. Accepting makes an unpublished draft on the new wording; defer and reject need a reason.

`preview_draft` returns an authenticated `previewPath` and a fit contract. `fit_check_draft` measures that exact preview in a browser on the server (below). `review_draft` is registered for MCP: it records approval of a preview this actor has already fit-checked on the server, and takes no measurement of its own; `humanApproved` is optional (still accepted as `true` from existing clients; `false` is refused). `publish_draft` accepts `{draftId, expectedVersion, previewId, confirmDuplicateName?}` (plus `workspace`) and the authoring service rejects it unless that exact preview/version/hash has a stored review receipt. When another published graphic already has the draft's name it is refused with a suggested name; `confirmDuplicateName:true` publishes under that suggestion, carrying the review, the measurement and the checked frame onto the renamed version.

### Artwork (packet A6)

- **`upload_asset`** adds an image to the workspace's artwork library in chunks, because a 512 KB image is too large for one comfortable tool argument and a function instance is not sticky between calls: `step:'begin'{name, altText, totalBytes}` returns an `uploadId` (open 15 minutes; at most 20 open per workspace), `step:'append'{uploadId, chunkIndex, dataBase64}` adds the next chunk in order (from 0, each at most 192 KB before base64; a skipped or repeated index, strict-base64 failure or a chunk past `totalBytes` is refused and adds nothing), and `step:'commit'{uploadId}` assembles it and stores it with the web upload's own rules (a non-animated PNG, JPEG or WebP, at most 512 KB, 4096 px per side and 16 megapixels, the workspace's 500-asset limit). The id is content-addressed, `asset_<sha256>`, so the same image twice is one asset and the result says `alreadyInLibrary`. Only the connection that began an upload can add to it or commit it. Chunks are staged in `workspace_asset_uploads` (`db/assets.sql`); until that table exists every step answers that uploading over the connection is not set up yet, and the web upload is unaffected.
- **`upload_asset` in one call (TBI redo G2).** Two forms need no chunking and no `step`:
  - `{importId, name, altText}` reads an image someone dropped on `open_import_dropzone{kind:'asset'}` (the import store holds up to 5 MB). An import of another kind, one still arriving, refused, expired or unknown is refused in a sentence that says what to do next.
  - `{url, name, altText}` fetches an https image from an allowlist: `image.singular.live`, `assets.singular.live`, and the workspace's own site (the hosts of `PUBLIC_BASE_URL`, each `PUBLIC_ALTERNATE_ORIGINS` entry and `canonicalOrigin()`). Nothing else is fetched: not http, not another host or port, not a link with a user name or password. Redirects are followed by hand, at most 3, and every hop is re-checked against the same list before it is requested. The whole fetch has 10 seconds, the download is capped at 10 MB (declared or streamed), and the response must say it is an image. No cookie or credential is sent. A refusal names the host, never the rest of the link, and changes nothing.
- **Fitting on the server.** Every form, the chunked one included, passes the image through `fitAssetImage` (`lib/assets.ts`) before `createAsset`, which stays the final check:
  - an image already within 512 KB, 4096 px per side and 16 megapixels is stored byte for byte, and sharp is never loaded;
  - a larger one is resized to fit (aspect ratio kept, never enlarged, turned upright by its EXIF orientation), its metadata stripped, and re-encoded. JPEG stays JPEG, with the quality stepped from 85 down to 60 until it fits. PNG is recompressed, then tried with a 256-colour palette, then becomes WebP with its transparency kept. WebP stays WebP. If the lowest quality still does not fit, the size shrinks by a fifth and the steps repeat, up to 8 rounds;
  - an animated image, anything but PNG, JPEG or WebP, or an input over 100 megapixels stays refused.
  - The result says `downscaled:false`, or `downscaled:true` with `original{type, bytes, width, height}`, `stored{type, bytes, width, height}` and `downscale`, a sentence saying what was done. The message leads with that sentence. The asset id is the sha256 of the stored bytes, so the same source image fitted twice is one asset.
  - Acceptance on TBI's files (local, 2026-09-24): the Donate QR (1410×1182, 80 KB) and TBI-Logo-Horiz (1050×750, 168 KB) are stored unchanged. 0001.jpg (8000×4500, 1.18 MB) becomes a 4096×2304 JPEG at quality 85, 436 KB.
- **`list_assets{includeArchived?, query?}`** (read only) returns compact rows: `id`, `name`, `altText`, `type`, `bytes`, `width`, `height`, `version`, `archived`, `published`, and `usedBy` — each draft that uses it, with whether that draft is published.
- **`archive_asset{assetId, expectedVersion}`** archives one image. It is refused, changing nothing, while a published graphic in the catalog uses it, in a sentence that names those graphics. Unpublished drafts that use it are named in the result: they will not publish until the artwork is restored (in the editor's library) or replaced.
- To use an image: `update_draft{patch:{presentation:{imageAssetId}}}` (or `presentation.imageAssetId` on `create_draft`), then `ship_draft`, whose frame shows the artwork and whose result says `artwork:'loaded'`.

### Dropped files (TBI redo G1)

A large file (a Singular extract, local sources, a deck plan, an image) is dropped on a web page instead of being retyped through tool arguments, and a tool then reads it by `importId`. The store is `lib/imports.ts` (`workspace_imports`, `db/imports.sql`, not applied; in memory under local rehearsal only, gated exactly like the artwork store). Until the table exists, opening a dropzone answers that dropped files are not set up yet.

- **`open_import_dropzone{workspace, kind, note?}`** returns `{importId, url, linkExpiresAt, kind, maxBytes, next}`. `kind` is `singular-extract`, `local-sources`, `asset` or `deck-plan`. `url` is `<origin>/import/<token>`: the link is the capability, like a signed URL, so it needs no sign-in, works for **30 minutes**, and should be shared only with the person who has the file. Only the token's sha256 is stored. `note` (at most 200 characters) is shown on the page. At most **10** dropzones wait for a file at once; expired imports are swept on each open. An import is kept **7 days**.
- **`get_import{workspace?, importId}`** (read only) returns `status` (`waiting`, `receiving`, `ready`, `refused`), `kind`, `fileName`, `mediaType`, `bytes`, `sha256`, `refusal`, `note`, `createdAt`, `linkExpiresAt`, `expiresAt`, and for a ready import a `summary` by kind: a Singular extract's `shape` (`nested` or `flat`), compositions per app and `total` (after normalising, as `import_singular_extract` would read it, or the first `problem`); local sources' `items`, distinct `keys` and `missingKey` (with the first indexes); a deck plan's `format`, `rows` and `columns`; an image's `mediaType`, `width` and `height` from its header. **It never returns the file.**
- **`list_imports{workspace?}`** (read only): the kept imports, newest first (at most 50), with the same fields and no summary or content.

**The page** (`app/import/[token]`, uploads to `POST /api/imports/<token>`, `lib/import-http.ts`) shows the congregation, what to drop, the size limit and when the link expires, with a drop area and a file picker. It sends `?step=begin {fileName, mediaType, totalBytes}`, then the bytes as `application/octet-stream` parts of at most **1 MB** (`?step=chunk&index=<n>`, in order; Vercel caps a body at 4.5 MB), then `?step=finish`. On finish the server computes the sha256 and checks the file by kind: JSON kinds must be UTF-8 JSON (a byte-order mark is allowed) within **2 MB**; a deck plan is UTF-8 CSV or JSON within 2 MB; an image must be PNG, JPEG or WebP **by its first bytes** within **5 MB** (G2 fits it to the artwork limits). Anything that looks like a credential (the `import_singular_extract` rule, on the parsed JSON or on each CSV line) is refused. A refusal is a sentence naming where, never what; the status becomes `ready` or `refused`. While the link is open, dropping again replaces the file. The page and its route send `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex` and `Cache-Control: no-store`, and nothing logs the token.

### Branding (packet L4)

A workspace's branding is stored as data in `workspace_branding` (`db/workspace-branding.sql`, one versioned row per workspace; not applied yet). The row holds only what the congregation changed; everything else resolves to the built-in identity, so a workspace with nothing stored renders exactly as it did before L4.

- **Colours** (`colors`, six-digit hex): `primary`, `deep` and `accent` (the workspace identity colours: title bar, gradient, circles and accent line), `ring` (the medallion ring; defaults to the accent, drawn at 90% opacity), `paper` (the lower third and panel background, drawn at 97%), `ink`, `titleText`, `accentTitle` (the Hebrew accent title) and `translationInk` (the translation line in panel rows). A stored accent moves the ring with it unless the ring is set on its own.
- **Font roles** (`fonts`): `latin` and `hebrew`, each one of the installed overlay faces the output waits for (lib/font-registry.ts: Noto Sans Hebrew and WorkRefresh; David Libre and Frank Ruhl Libre too where book faces are on). A new face is a code change and a release. The book-faces trial, where on, still wins over a font role.
- **Artwork** (`artwork`, asset ids from `list_assets`): `logo` (the medallion on every graphic without its own artwork), `restingLogo` (the standing corner mark, only where the workspace has that capability; branding never switches it on) and `scanCard` (stored; the scan card does not draw artwork yet). Artwork named here is marked published, so the public output page can load it.

How it reaches the screen: `/api/workspace` applies the stored branding (identity colours, logo, resting logo, plus a `branding` object with the full resolved set); every renderer builds its branding from that response, and the Player sets each value as a CSS variable on the overlay box (`--crc-ring`, `--crc-paper`, `--crc-base`, `--crc-ink`, `--crc-title-ink`, `--crc-accent-title`, `--crc-translation-ink`, `--crc-font-latin`, `--crc-font-hebrew`, beside the existing four). app/overlay.css reads each as `var(--x, <the old literal>)`; no rule moved. The server fit stage reads the same branded workspace. A branding read that fails or takes longer than 1.5 s serves the built-in identity, so the output page always starts. An output page that is already open keeps its branding until it is reloaded.

- **`get_branding`** (read only) returns `version` (0 when nothing is stored), each colour with its value, built-in value, whether it is set and what it paints, the font roles with the faces this workspace can use, and the artwork.
- **`preview_branding{colors?, fonts?, artwork?, cueIds?}`** (read only) draws one catalog graphic per layout (bottom, left, right, corner), or up to four named by `cueIds`, in the server browser with the change applied, and returns one frame per graphic as MCP images in order (each row's `previewImage.frame` is its image's position). Nothing is saved. Artwork not yet published reaches the stage by a signed link. It stops starting new frames after 40 s and marks the rest `skipped`.
- **`update_branding{workspace, expectedVersion, colors?, fonts?, artwork?}`** saves a change: name only what changes, and `null` puts a value back to the built-in one. A stale `expectedVersion`, an unknown or archived asset, a face not installed, or an empty change is refused in a sentence and changes nothing. Until the table exists every write is refused with a sentence and reads return the built-in branding.

### One-call publish and the publications list (packet A2)

- **`ship_draft{workspace, draftId, expectedVersion, allowRename?}`** runs `preview_draft` → `fit_check_draft` (with the frame) → the attested review → `publish_draft` as one call, each step the same operation as above. So a graphic goes from nothing to published in two calls: `create_draft` (or `compose_custom_draft`), then `ship_draft`. It answers `shipped:true` with the frame as MCP image content, `verdict`, `revision`, the final `name` (and `renamedFrom` when it took the suggestion), the new `draftVersion`, and the receipt. Otherwise it answers `shipped:false` with nothing published and `stoppedAt` saying where:
  - `duplicate_name` — checked before any browser opens; carries `suggestedName`. Call again with `allowRename:true` to publish under it.
  - `validation` — the preview's own errors.
  - `fit_failed` — `fitErrors` are the renderer's own sentences, word for word, and the frame comes back as an image so the agent sees what failed.
  - `fit_unavailable` — the unavailable sentence and `fitCheckUrl`, as `fit_check_draft` gives them.
  The review inside `ship_draft` is always the attested one, whoever calls, because the check it stands on is the one the call just ran. One graphic per call; a batch is one `ship_draft` per item.
  Duration, measured 2026-09-23 on Windows with local Chrome (`channel:'chrome'`, playwright-core 1.63.0; every fit launches and closes its own browser): the server fit alone took 1.10, 0.95, 0.87 and 0.81 s over four runs; a whole `ship_draft` through `POST /api/authoring` on a `next dev` server took 6.5 s on the first call after the server started (first load of the fit module and the stage) and 1.0–1.3 s after. The stage was the configured public origin's `/author/fit-stage`, as it always is without a request. Not measured: a Vercel cold start, which adds unpacking the `@sparticuz/chromium` pack on Linux. The fit's own 25 s deadline sits inside the routes' `maxDuration=60`, and the rest of the call is database work, so one ship fits; a batch must not share a call.
- **Receipts say who approved.** Every review receipt records `approvedBy: 'agent' | 'person'` and `member`: for an agent, the member who approved the connection (from the actor `mcp:<client>:member:<id>`); for a person, their member id. A person's receipt still carries `humanApproved:true`; an agent's no longer claims it. Receipts written before this change carry only `humanApproved:true` and still satisfy the publish gate.
- **The checked frame is kept.** When `fit_check_draft` (or `ship_draft`) captures a frame it is stored with the preview it measured, in `authoring_preview_images` (`db/authoring.sql`: one row per preview, `bytea`, at most 750 KB, removed with the preview). The result says `imageStored`. Keeping it is best effort: a frame over the bound, or a database where the table has not been created yet, is simply not kept, and the verdict and the publish are unaffected. Only the server fit's own frame is kept; `preview_content` still stores nothing.
- **`list_recent_publications{since?, actor?, limit?}`** (read only) lists publications since `since` (milliseconds; default the last 7 days), newest first: name, layout, an excerpt, when, `publishedBy` and `approvedBy` (`agent` or `person`), `member`, whether it is still the live version (`current`), whether it is archived, whether its frame was kept (`image`), and `rollbackTo` — the revision `rollback_draft` would restore (the revision before it, offered only while it is live and not the first). `actor` narrows to agent or person publications.
- **The web review page** `/author/publications` (linked from the library as *Recent publications*) shows the same list to signed-in Administrators and Editors — by default only what an assistant published, over the last day, week or month — with the stored frame beside each one and **Go back to the previous version**, which calls the existing `rollback_draft`. It reads `GET /api/authoring/publications` (the list, with member names in place of member ids) and `GET /api/authoring/publications?image=<preview>` (the frame; author session required). No ids are shown. A first publication has no earlier version, so the page says so rather than offering to go back; taking one out of use altogether is retirement (packet A3).

### Catalog hygiene (packet A5)

Five tools in `lib/catalog-hygiene.ts` (schemas in `lib/catalog-hygiene-schemas.ts`). None writes a draft directly: every change is `update_draft`, `style_draft`, `archive_draft`, `ship_draft` or `retire_cue`, run per item through the authoring service, so versions, source pins, the name check and the publish gate are the single-tool ones.

- **`find_catalog_issues{kinds?, limit?}`** (read only) returns `issues[]`, each with `kind`, `graphics` (id, name, draft version, published; built-in graphics are marked `builtIn`), a plain `message`, and `suggestedFix{tool, how}`; plus `counts` per kind, `total`, `truncated` (default limit 100) and `checked` (how many drafts and built-ins were read, and whether services and the deck could be). Kinds:
  - `duplicate_content` — drafts that read exactly the same on screen (layout, texts, rows; what `cueHash` hashes, less id, name and pins, since `cueHash` includes the id and never repeats). Fix: `batch_update` archive, or `supersede_cue` when more than one is published.
  - `duplicate_name` / `near_duplicate_name` — the same name, or copies of one ("Copy of Copy of Thank you", "Thank you (2)", "Thank you copy"), across live drafts and the built-in graphics they have not replaced. Parenthesised qualifiers other than a number are kept, so "Lecha Dodi (Carlebach)" and "(Sulzer)" are distinct. Fix: `batch_update` rename or archive.
  - `inherited_title` — the on-screen title shares no word with the graphic's own name and does not appear in its text, but is another graphic's title (Zochreinu showing "Mi Chamocha"). Fix: `batch_update` rename with `title`.
  - `archived_but_published` — archived in the editor, still in the live library. Fix: `batch_retire` (the result's `batchRetire{items}` lists every one found as `{draftId, expectedVersion}`, whatever `limit` cut from `issues`, ready to send), `retire_cue` for one, or `restore_draft`.
  - `retired_in_service` / `retired_on_deck` — a retired graphic still used by a prepared service (entries or coverage) or fired by a stored Companion deck key (`buttons` gives page, row, column, label; the retired check is `catalogCueLookups` from `lib/companion-deck/validate.ts`). Fix: `supersede_cue`.
  - `restored_name_clash` — two live graphics with one name, because one came back (restore or rollback) after the other was published under that name; ordered oldest publication first. Fix: `batch_update` rename then `batch_ship`, or `retire_cue`.
  - `unpublished_changes` — published, and the draft now reads differently from the live graphic (a version bump alone, as retire and restore make, does not count). Fix: `batch_ship`.
  The deck is the one the deck tools (C3) store (`deckSourceForDeployment` in lib/companion-deck/tools.ts; CRC's is seeded on first read). Where none is stored (TBI before `seed_deck_from_export`, or db/companion-decks.sql not applied) `retired_on_deck` says so in `checked.deck` rather than reporting nothing silently.
- **`batch_update{workspace, items[], dryRun?}`** — up to 100 items, each `{action:'rename', draftId, expectedVersion, name?, title?, accentTitle?}`, `{action:'style', draftId, expectedVersion, layout?, arrangement?, rowOrder?, comfortableTypography?, latinLineBreaks?}` or `{action:'archive', draftId, expectedVersion}`. Dry run by default: each item says `planned`, `unchanged` or `failed` (a stale version, an unknown draft, a set member to archive) and nothing changes. With `dryRun:false` the items run one after another and a failed item is that item's result (`error{code, message}`); the rest still run. It never publishes: a renamed published graphic keeps its old wording on screen until it is shipped.
- **`batch_ship{workspace, items[], cursor?, dryRun?}`** — up to 200 items `{draftId, expectedVersion, allowRename?}`. Dry run by default: version, validation and the name clash are checked without opening a browser (`would_ship`, `would_stop` with `stoppedAt`, `already_published`, `failed`). With `dryRun:false` each item is exactly one `ship_draft`. `maxDuration` is 60 s and a cold server fit is slow, so a call starts a new item only while it projects to finish inside 40 s (elapsed time plus the slowest item so far, at least 10 s); the first item always runs. Items left over come back as `nextCursor` (`remaining`, `done:false`); call again with the same items and that cursor. A cursor is bound to its list and refused for another. Per-item `status`: `shipped` (name, revision, verdict), `stopped` (`stoppedAt` and the sentence, nothing published), `failed`, or `already_published` — an item already live at that version is skipped, so repeating a chunk never publishes twice. Frames are not returned; `ship_draft` is the call for one graphic with its image. A chunk that shipped anything refreshes the relay catalog as `ship_draft` does.
- **`batch_retire{workspace, items[], dryRun?}`** (TBI redo G8) — up to 200 items `{draftId, expectedVersion}` (the draft id is the cue id `retire_cue` takes). Its own tool rather than a `batch_update` action because it changes the live library (`destructiveHint`), and `batch_update` never does. Dry run by default: nothing is written, and each item says `would-retire`, `already-retired` or `refused` with `code` and `reason`. With `dryRun:false` each item is one `retire_cue`, one after another; a refused item is that item's result and the rest still run. Per item: `index`, `draftId`, `expectedVersion`, `status` (`retired`, `would-retire`, `already-retired`, `refused`), `name`, `version` (after the retire), `revision` (the one `restore_cue` brings back), `reason`. The refusals are `retire_cue`'s own sentences (`lib/retire-rules.ts`, shared by both), each ending "Nothing was changed.": `unknown_cue`, `not_a_draft` (a built-in graphic: `import_cue` first), `not_published` (archive it instead), `version_conflict` (per item: read it again and retry that item), and `duplicate_item` for a draft listed twice in one call. An already retired graphic is `already-retired` whatever version was sent, so repeating an interrupted call is safe. `retire_cue` refuses nothing for being on air, in a service or on a deck key, so neither does the batch: a graphic on screen stays there until it is taken out, and `find_catalog_issues` (`retired_in_service`, `retired_on_deck`) lists what still uses a retired graphic afterwards. A part of a multipart set retires alone, as with `retire_cue`; an item whose other published parts are not in the call carries a `setWarning` naming them. The answer has `total`, `wouldRetire` or `retired`, `alreadyRetired`, `refused` and, applied, `liveCatalogChanged`; an apply that retired anything refreshes the relay catalog once (the same `syncLiveCatalog` as `retire_cue`), so `/api/catalog` and the relay drop them. A retired graphic's name is free: `ship_draft` and `batch_ship` measure names against the live library, which retired graphics have left, so a copy with the same name ships under its own name with no `duplicate_name` stop and no `allowRename`. Order for a redo: retire the first pass, then ship the new set.
- **`supersede_cue{workspace, old, new, expectedVersion, dryRun?}`** — `expectedVersion` is the old graphic's draft version, as for `retire_cue`; `new` must be in the live library. Dry run by default: lists every prepared service (archived ones included) whose entries, coverage decisions or review candidates name `old`, and every deck key bound to it. Applied, it rewrites those services (each at the version it was read), then the deck (one optimistic write), then retires `old` through `retire_cue`. Row and key labels are left as they are (no silent rewording). An already retired `old` is repointed without a second retire. If a write fails the answer says `complete:false` and which part was not changed; running it again finishes the rest.


### House defaults and the batch copy (packet T1)

- **House defaults.** `get_authoring_defaults` returns this workspace's defaults, their `version` (0 when none are set) and where they apply. `update_authoring_defaults{expectedVersion, ...}` sets them: a field replaces the stored one, `null` clears it, a field left out stays; a stale `expectedVersion` is refused in a sentence and a write that changes nothing keeps the version. The fields are `textSize` (a named size) or `fontSizes` (explicit Hebrew/transliteration/title sizes, which win over it), `lineSpacing`, `latinLineBreaks`, `rowOrder`, `translation` (`include` or `omit`), `arrangement` (`together` or `blocks`) and `layoutRule {maxLowerThirds, sequenceLayout}` (the house rule "more than two lower thirds becomes a left sequence" is `{maxLowerThirds:2, sequenceLayout:'left'}`). Storage is one row per workspace in `authoring_defaults` (`db/authoring-defaults.sql`, not yet applied: until it is, reads return no defaults and writes are refused in words); rehearsal and tests use an in-memory store.
- **Where they apply.** `create_draft` (and `compose_custom_draft`, which goes through it), `create_source_draft_set`, `customize_shared_cue`, `customize_shared_set` and `customize_shared_batch`. Whatever the call names wins: a `textSize` or any explicit font size keeps the caller's typography, and a content `arrangement`, `rowOrder`, `includeTranslation` or `layers` keeps the caller's choice. `applyDefaults:false` skips them for one call. On a shared-library copy the house typography replaces the copied sizes. A translation default the selected source can't honour is skipped and reported, never a refusal. The layout rule applies where a set is formed: `create_source_draft_set` on the lower third with more pages than the rule allows is made on the sequence layout instead (a named lower-third `templateCueId` keeps the lower thirds); a copied lower-third set keeps its own shape and carries a note. Results carry `houseDefaults {applied, skipped}` only when something was applied or skipped, and a draft the defaults shaped records `houseDefaultsVersion`; with no defaults stored every result and draft is exactly as before. Existing drafts never change when the defaults do.
- **Batch copy.** `customize_shared_batch{items[], applyDefaults?, dryRun}` copies up to 50 items per call, each `{cueId, expectedCueHash?, name?, applyDefaults?}` or `{setId, expectedCueHashes?, applyDefaults?}`, through the same paths as `customize_shared_cue` and `customize_shared_set`: source snapshots with their attribution, pins and the `sharedFrom` upstream link are kept, and nothing is published. `dryRun` defaults to true: nothing is written (no artwork import either) and each item says `would-create`, `already-copied` or `refused` with a sentence, with what the defaults would change, plus an `apply` object (every item with its current cue hashes) to send back with `dryRun:false`. Items are independent: an unknown id, a changed upstream hash or a repeated item is refused on its own line and the rest continue. More than 50 items is refused before anything is copied.
- **Resumable.** An item is `already-copied` when a live draft here was copied from that exact upstream version (cue id and cue hash; for a set, a whole set in the same order). Each item is its own insert, so a call that stops part way keeps its finished items, and the same call again skips them and copies the rest. A copy of an earlier upstream version is left alone and noted; a new copy of the current version is made.

### Workspace-owned sources (packet T2)

A congregation enters its own readings (a Mishkan T'filah page, a song setting) once, as sources, and authors from them exactly as from the corpus. `lib/local-sources.ts`; storage `db/local-sources.sql` (per workspace, optimistic version; not yet applied), in memory under rehearsal.

- **`add_local_source{name, kind?, book?, page?, section?, service?, attribution?, licence?, aliases?, blocks}`.** Each block is `{he, tr}` (Hebrew with its transliteration, optionally `en`, its translation), `{tr}` or `{tr, en}` (a line sung in transliteration, with or without its English; G3), or `{en}` alone (an English reading). Hebrew without its transliteration is refused. Up to 48 blocks, 2000 characters a channel, 20000 in all. `attribution` and `licence` are optional and stored exactly as given; nothing is inferred about coverage, and an empty attribution is refused (leave it out for no credit). The same name on the same book and page is refused; a page may hold several sources. Ids are `local:<uuid>`.
- **Kinds and position (G3).** `kind` is `'prayer-book reading'` (the default, and what every record entered before G3 reads as), `'song setting'` or `'tbi text'` (the congregation's own). `book` and `page` are optional: a page needs its book, and a prayer-book reading from a named book needs its page; a song setting or a text may have neither, and a prayer-book reading may have no book at all (a High Holy Day prayer no book prints). With no book a source has no book facet and no outline; with no page it has no folio and no liturgy position, and is found by name, text and kind (`search_sources{query:'song setting'}`). Uniqueness is one name per book and page when both are set, and one name per kind among the sources with no printed page. `kind` joins the unit hash only when a record has one, so a record that uses none of the new fields keeps its `unitSha256` and block hashes (tests/local-sources-import.test.ts).
- **No credit (G3).** `attribution` may be absent for any kind, and is never invented. The source then reports `attribution:null, credit:'not credited'` in `list_local_sources`, `search_sources`, `get_source` (`local`) and a draft's `provenance[]`, and a graphic built on it carries no credit line. `update_local_source{attribution:null}` clears one.
- **Transliteration-only lines (G3).** `{tr}` is stored as a `bilingual` block with no Hebrew; its `en`, if any, is that block's `translation-en`, paired as the corpus pairs its own. The renderer draws it as a transliteration row (`row-transliteration`, the `textMainEng` channel) with its English as the translation row, and never an empty Hebrew row: the Hebrew channel skips it, `textMainheb` is left out when nothing in it is Hebrew, and an arrangement in blocks drops an empty row. A lower third of sung lines alone draws the transliteration column by itself.

- **`update_local_source{sourceId, expectedVersion, ...}`.** Fields left out stay; `blocks` replaces every block; `null` clears `book`, `page`, `attribution`, `section`, `service` or `licence`, under the same position rules. A stale `expectedVersion` is refused and writes nothing; a no-op write keeps the version. Any change to what the unit says or where it sits (name, book, page, section, attribution, licence, blocks) moves its `unitSha256`; aliases and service only help search.
- **`list_local_sources{query?, kind?, book?, page?, limit?}`.** Printed sources by book and page, then those with no book. Each source with its kind, version, attribution, licence, block ids, and `usedBy` (the drafts that pin it, `stale` when a draft pins an earlier wording).
- **Merged into the corpus this workspace sees.** `search_sources` finds them by text and by `book` (printed title or slug, e.g. `mishkan-tfilah`) with the new `page` filter (which narrows corpus units by folio too); compact rows mark them `local:true` with their `attribution`. `get_source` returns one with its own authority (its licence text, never the corpus licence) and `local{book, page, attribution, licence, version}`. `list_book_units` and `list_source_facets` include them. `create_draft`, `create_source_draft_set`, `preview_content` and `update_draft` accept their block ids.
- **Source-backed like corpus drafts.** A draft pins the unit and block hashes and keeps a snapshot; `create_draft` and `preview_draft` return `provenance[]` (book, page, attribution, licence) and the published cue carries the snapshot, so the graphic carries its attribution as data. It is not drawn on screen; to show a credit, enter it as a final `{en:'~ Attribution'}` block (a marked attribution, which `create_source_draft_set` keeps with the text before it on a lower third). After an edit, pinned drafts keep their wording until refreshed: `scan_source_changes` records the change in the source-change inbox, and `update_draft{refreshSourceIds:[id], patch:{content}}` rebases one. `rollback_draft` checks a local revision against the current unit, as for the corpus.
- **Book and page matching.** A published graphic built on a local source reports its position (`liturgyForCue`: book slug and page) from the snapshot it pins, so `prepare_service_from_setlist` matches a setlist row's `{book, folio}` to it. Setlist books now match ignoring case and punctuation, so `Mishkan T'filah` and `mishkan-tfilah` meet. Deck conversion can use `localSourcesAt(units, book, page)` / `findLocalSourcesAt(repo, book, page)`.
- **`import_local_sources{workspace, importId | sources[], dryRun?}` (G3).** Many sources in one call, from a dropped file (`open_import_dropzone{kind:'local-sources'}`; a JSON array, or `{items:[...]}`, at most 200 items) or up to 100 items inline. Each item is the build-prep shape (work/tbi-redo/build-prep/SPEC.md): `key, name, kind, book, page, section, service, attribution, licence, aliases, blocks[{he, tr, en}]`, where `null` means not given. Planning fields (`title`, `accentTitle`, `layout`, `panels`, `buttons`, `changes`, `missing`, `rowConfidence`, `notes`, `folds`, `stripped`, `rowCheckReason`, any other) are ignored, and listed once in `ignored`, never refused. It is idempotent by `key` (a build key of kind `local-source`, lib/build-keys.ts): a new key creates a source; a key seen before updates the same source when anything changed, else reports it `unchanged`; a key whose source is gone creates a new one and moves the key (`movedKey:true`). One bad item never stops the rest. Each item reports `index, key, status` (`created`, `updated`, `unchanged`, `refused`, or on a dry run `would-create`, `would-update`), `sourceId`, `version`, `reason` when refused, and `blockSha256[]`: per stored block, sha256 (hex) of the UTF-8 JSON array `[he, tr, en]` exactly as stored, `null` for an absent channel, so the caller can prove every block round-tripped byte for byte. Text is stored as given apart from the one normalisation every local source gets (CRLF to LF, trim); an item whose block that changed lists it in `normalised[{block, channel, change}]`. The result has `totals`, and `keys` mapping each key to its `local:` id. `dryRun:true` writes nothing, not even a key. The key is written before the source, so a failed insert is repaired by the next run.
- **Never shared upstream.** The shared-library export skips every graphic built on a local source, so neither it, its wording nor its attribution leaves the workspace (tests/local-sources.test.ts).

`preview_draft` returns an authenticated `previewPath` and a fit contract. `fit_check_draft` measures that exact preview in a browser on the server (below). `review_draft` is registered for MCP: it records approval of a preview this actor has already fit-checked on the server, and takes no measurement of its own. `publish_draft` accepts only `{draftId, expectedVersion, previewId}` (plus `workspace`) and the authoring service rejects it unless that exact preview/version/hash has a stored review receipt.

### Batch drafts from a build plan (packet G4)

`batch_create_drafts{workspace, items[], applyDefaults?, dryRun?}` makes up to 50 unpublished drafts per call from a build plan (`lib/batch-drafts.ts`, schema `lib/batch-drafts-schema.ts`). Every item has the caller's stable `key` (`lib/build-keys.ts`: 1-120 of `a-z 0-9 . _ : -`) and a `type`:

- **`source`**: one source-backed graphic. The source is `sourceId` (a corpus id or `local:` id) or `sourceKey` (the `local-source` key `import_local_sources` recorded). The blocks are `blockIds` (from `search_sources` with `includeBlocks:true`) or, for a local source only, `blocks` (its block positions, 0 first), resolved to that source's own block ids (`<id>#block-<n>`). `mode` defaults from the blocks: `bilingual` when every one pairs Hebrew and transliteration, `original-en` when every one is English; a mix is refused, because one graphic shows one kind (split it into a set's panels). Naming a translation block asks for the translation (`includeTranslation`). Also `title`, `name` (default the title), `accentTitle`, `layout`, `templateCueId`, `textSize`, `presentation`, and for bilingual text `includeTranslation`, `arrangement`, `rowOrder`.
- **`set`**: the same source fields with `panels[{blockIds} | {blocks}]`, one graphic per panel in order, each panel its own kind. Every panel is built and validated by `create_draft` without being stored; then all of them are stored as one set in the `create_source_draft_set` shape (`<name> — 01 of 03`, the title on each, one manifest), or none is. The house layout rule does not re-split explicit panels. A whole source split automatically is still `create_source_draft_set`.
- **`slide`**: custom text (`text`, content mode `custom`) with `title`, `layout`, and an optional `imageAssetId` (`presentation.imageAssetId`, from `upload_asset`).
- **`customize_shared`**: a shared-library copy, `{cueId, expectedCueHash?, name?}` or `{setId, expectedCueHashes?}`, run as a one-item `customize_shared_batch`. A copy already made from the same upstream version is found rather than duplicated, and the key is recorded for it.

Every item runs through `create_draft` or `customize_shared_batch`, so their validation, pins, provenance and house defaults are the ones applied: house defaults apply exactly as on those tools, and `applyDefaults:false` (per call, or per item, which wins) skips them.

- **Idempotent by key.** A key already recorded (kind `draft`, or `draft-set` for a set or a shared set) whose draft or set is still live answers `exists` with its ids and current versions, and nothing is made. An archived target no longer holds its key: the item is made again and the key moves. A key recorded for the other kind (a single graphic where the item is a set, or the reverse) is refused. Each new item's key is recorded as it is made; if the key store cannot write (`db/build-keys.sql` not applied), that item reports it and every later item is refused unattempted, so no draft is made without its key.
- **Per-item results.** `items[]` rows are `{item, key, type, status, draftId, version}` for a single graphic or `{..., setId, drafts:[{draftId, version}]}` for a set, with `reason` on a refusal (a sentence ending "Nothing was created for this item") and `warnings` / `houseDefaults` / `notes` when the underlying tool gave them. `status` is `created`, `exists`, `would-create` or `refused`. One refusal never stops the rest; a repeated key in one call is refused on its own line. Over MCP the schema is checked before the call runs; by `/api/authoring` a malformed item is refused on its own line.
- **Dry run by default.** Every item is checked as far as it can be without writing: source, blocks, mode, `create_draft`'s own validation and the shared-library plan. Nothing is stored and no key recorded. `dryRun:false` creates.
- **Ship in one call.** `batchShip` is a ready `batch_ship` input (`{items:[{draftId, expectedVersion}], dryRun:false}`) naming every draft made or found, set members included, in item order; past 200 drafts the rest follow in `batchShipMore`. A dry run names only drafts that already exist.
- **Limits.** More than 50 items is refused in a sentence before anything runs. Publishes nothing.

### Review boards (packet T4)

A review board puts a set of graphics in front of a person on one web page and hands their answers back to the agent. It publishes nothing and puts nothing on screen. Tools (authoring scope; changes take `workspace`):

- **`create_review_board{workspace, title, draftIds, grouping?, groupLabels?, references?}`** creates a board of 1–400 drafts and returns `boardId`, `version`, `url` (`/author/review/<boardId>` on this congregation's host), `counts` and `groups`. Unknown draft ids are refused; an unpublished draft is accepted with a warning and shows no picture until it is published. `grouping`:
  - `none` (default): one list in the order given;
  - `deck-page`: the stored Companion deck's pages, lowest page first, then row and column; a graphic on no page goes under *Not on the deck yet*. The lookup reads the deck C3 stores (CRC's is seeded on first read); where none is stored yet (TBI before `seed_deck_from_export`) this is refused unless `groupLabels` is given;
  - `service`: the prepared service each graphic is in (services by name; a graphic in several goes under the first), in that service's row order; others under *Not in a prepared service*.
  `groupLabels` (draft id → a heading in plain words, e.g. "Page 3: Shabbat evening") overrides the grouping, in first-appearance order; unlabelled drafts go under *Other graphics*. `references` (draft id → `{origin, app?, comp?, text, imageAssetId?}`) is what the old deck showed; a draft that carries a `reference` of that shape (packet T3) shows it without being passed.
- **`get_review_board{boardId, filter?}`** (read only) returns `counts` (`items`, `approved`, `needsChange`, `undecided`, `updatedSinceAnswered`, `withoutPicture`) and one line per graphic: `draftId`, `name`, `group`, `decision` (`approve`, `needs-change` or `null`), `note`, `decidedAt`, `decidedBy` (member id), `decidedRevision`, `currentRevision`, `hasPicture`, `hasReference`, and `updated`/`earlier` as below. `filter` narrows to `needs-change`, `undecided`, `approved` or `updated`.
- **`update_review_board{workspace, boardId, expectedVersion, title?, add?, remove?, groupLabels?, references?, dropAnswers?}`** adds, removes or renames, with the version you read (answers never change the version, so a reviewer clicking does not block the agent). Removing a graphic the reviewer already answered is refused with those answers listed until `dropAnswers:true`; a removed graphic's answer goes with it.

**Updated since you looked.** Each answer records the revision the reviewer was shown. When the graphic is republished (or rolled back) after that, the board shows it as *Updated since you looked* with the new frame, and it counts as undecided again: `get_review_board` gives `decision:null`, `updated:true` and the earlier answer and note under `earlier`. When the reviewer answers again the item is settled; the earlier answer stays on record with it. A fix needs no board change: republish (`ship_draft`) and the board picks it up.

**The page** `/author/review/<boardId>` is for any signed-in member (Administrator, Editor or Operator); a paired device or a shared key is refused. Per graphic it shows the frame the server fit kept for the revision in use (A2's `authoring_preview_images`) or "No picture yet — ask the assistant to check it", the old slide's words (and picture) under *Before* when there is a reference, **Approve** / **Needs change** and a note. A click saves at once; a note saves when the reviewer pauses or leaves the box. No ids, codes or tool names are shown; controls are at least 44 px tall and the cards stack to one column below 860 px. It reads `GET /api/review-boards?board=<id>` (member names in place of ids), `GET /api/review-boards?board=<id>&image=<preview>` (only a frame that board is showing) and saves with `POST /api/review-boards`. Storage: `review_boards` and `review_board_answers` (`db/review-boards.sql`, not yet applied; in memory under local rehearsal).

### Layouts as data (packet L3)

A congregation can add its own card layouts (a top-right "Response" card, say) and publish graphics in them with no code change and no release. The four built-in layouts (bottom, left, right, corner) stay code and read only; the lower third and the panels are layered CSS and cannot be copied, the corner card can. Operations live in lib/layout-tools.ts; definitions are versioned in `layout_definitions` (db/layout-definitions.sql, not yet applied: until it is, reads show no data layouts and writes refuse in a sentence; in memory under local rehearsal). Tools (authoring scope; changes take `workspace`):

- **`list_layouts`** (read only): the built-in four and this congregation's own, each own layout with `newestVersion`, `status` (draft or published), `publishedVersion` and `usable` (it has a published version, so `create_draft` accepts it).
- **`get_layout{layoutId, version?}`** (read only, full record): the document (label, capabilities, card geometry and fit, motion) at the newest version or the one named, every version with its status and sha256, `pinnedGraphics` (published graphics per pinned version) and the static check. A built-in layout comes back read only, with its card when it has one.
- **`create_layout{workspace, layoutId, from, fromVersion?, label?, capabilities?, card?, motion?}`** copies `corner` or a layout of your own (its published version unless `fromVersion` says otherwise), merges `card` field by field, and saves draft version 1. The Response card is `{layoutId:'response', from:'corner', label:'Response card', card:{frame:{anchor:'top-right'}}}`.
- **`update_layout{workspace, layoutId, expectedVersion, label?, capabilities?, card?, motion?}`** writes only a draft: a draft newest version is changed in place; on a published newest version the change becomes draft N+1 (`openedDraft:true`), and version N and every graphic pinning it stay exactly as they are. `card` merges; `motion` replaces.
- **`validate_layout{layoutId, version?}`** (read only), static: the document parses (strict, everything inside the 1920x1080 frame and inside the card), no overlap between the title lane, the logo and the Hebrew/transliteration/single channels (the single channel is not compared with the other two: it stands in for them), `fit.floor` ≥ 20 and at or below every font size, the id matches Companion's `/^[a-z][a-z0-9_-]{0,39}$/` and is not built in, and every face the card draws with (WorkRefresh, Noto Sans Hebrew; `CARD_FACES`) is a registered, awaited face in lib/font-registry.ts. A card definition has no font field yet, so the font check guards the faces the card CSS uses. Each check is listed; failures are sentences.
- **`preview_layout{layoutId, version?, samples?, draftIds?, includePreviewImages?}`** (read only): up to six sample texts (`{label?, title, accentTitle?, hebrew?, transliteration?}` or `{…, english}`) and/or drafts by id, each drawn in this layout at that version (draft or published) and fitted by the server fit, frames returned as MCP images in sample order (`samples[i].previewImage.frame` is the image's number). With neither, the three standard samples `publish_layout` checks. A draft that includes a translation is reported as not drawable (a card shows Hebrew with transliteration, or one line). Nothing is saved.
- **`publish_layout{workspace, layoutId, expectedVersion, samples?}`**: the newest version must be the draft named. It runs the static check, then fits the standard samples plus up to three of your own, and publishes only if all pass; otherwise `{published:false, stoppedAt:'validation'|'fit_failed'|'fit_unavailable', message}` and nothing changes. Publishing registers the layout in this process at once.
- **`rebase_to_layout{workspace, layoutId, expectedVersion, dryRun?, draftIds?}`**: `expectedVersion` is the newest published version to move to. Dry run by default: lists published graphics pinning an older version (`would-rebase`) and those it will skip (draft missing, archived, or with unpublished changes, since a rebase must publish nothing but the new layout). With `dryRun:false` each is republished through `ship_draft` (preview, server fit with the new definition, attested review, publish), per-item results, no stop on the first failure; it starts no new graphic after ~40 s, so call again to continue (already moved graphics are no longer behind). The live library is re-synced when anything moved.

**Layout ids in the other tools.** `create_draft`'s (and every existing tool's) `layout` stays the registry enum from `layoutId()` in lib/mcp/shared.ts, built as each request's server is built. The MCP route registers the workspace's published layouts first (`ensurePublishedLayoutsRegistered`, re-read at most every 30 s, so a layout published on another instance arrives within that), and `authoringOperation` does the same before any validation. So a newly published layout is accepted on the next call and shows in the next `tools/list`, while the recorded schemas of existing tools are unchanged for a workspace with no data layouts. The layout tools themselves take any id in Companion's grammar as a plain string and answer an unknown one in a sentence.

**Fits and previews carry the definition.** A draft in a data layout pins `layoutRef{id, version, sha256}` (L2); every server fit is handed the pinned definition (`layouts`, resolved from the store, or the draft version for `preview_layout`) through lib/server-fit.ts to the fit stage, whose Player draws the card from it and whose checks (`findFitErrors`, `panelFillRatio`, `findFitWarnings` in app/author/preview.ts) read the card's height ceiling and fill from it. The editor dock and console previews do not pass `layouts` yet, so a data-layout draft opened in the web editor previews without its card.

## Server-side fit check (`fit_check_draft`)

`fit_check_draft` accepts `{draftId, expectedVersion, previewId}` and measures that exact preview in a real browser running on the server, so an MCP client gets the same verdict the editor computes. It launches headless Chromium, opens this deployment's own `/author/fit-stage` — an unlinked, data-free, credential-free page that mounts the real `Player` and calls the same `findFitErrors`, `findFitWarnings` and `panelFillRatio` the editor and `/author/fit-check` call — measures one 1920x1080 frame, and closes the browser. Nothing is published and nothing reaches live output.

Responses:

- `{verdict:'pass', fitErrors:[], warnings, fill, artwork, measuredAt, rendererVersion, message}` — `message` is "Checked in a browser on the server — no fit problems found.", or, when `artwork` is `'not-loaded'`, "Checked in a browser on the server — no fit problems found. The artwork was not loaded on the server; confirm it in the editor."
- `{verdict:'fail', fitErrors, warnings, fill, measuredAt, rendererVersion}` — `fitErrors` are the renderer's own sentences, word for word.
- `{verdict:'unavailable', reason, fitCheckUrl, message}` — `message` is "The server could not open a browser to check this graphic. Open Fit check and review it yourself.", and `fitCheckUrl` is `/author/fit-check?draft=<id>`. `reason` is one of `browser_unavailable`, `deadline_exceeded`, `measurement_invalid`.

Artwork (packet A6, R-B1): the stage holds no session, so each server fit is handed a signed read link for the cue's one asset, `/api/assets/<id>/signed?exp=…&sig=…`, and loads the artwork through it. The link is an HMAC-SHA256 over the workspace id, that asset id and the expiry, keyed from `RELAY_SECRET` (the secret that already signs the short-lived relay tickets) under a label of its own, so it cannot be replayed as a relay ticket; it expires five minutes after it is made, works for no other asset id, travels to the stage in the `__measureCue` argument (never in the stage URL), is never logged by this code and never appears in a tool result. The route answers a bad, expired or other-asset signature with 403 and serves the bytes `private, no-store`. So when the artwork rendered, `artwork` is `loaded` and the pass message carries no caveat; `not-loaded` now means it really did not render (for example a deployment without `RELAY_SECRET`, where nothing is signed), and `none` that the cue has no image. An image that does not load also stops the stage's asset wait, so that check reports `fail` with "Fonts or artwork did not load in time." (observed 2026-09-23 with signing off; it was also what every artwork graphic got before this change). It stays a label and never a gate — `findFitErrors` does not evaluate artwork. The published catalog still reads published artwork from `/api/assets/<id>/content`; the editor still reads drafts' artwork from the author-only `/api/assets/<id>/preview`. Note that the platform's own request logs record request URLs, signature included; a logged link is dead within five minutes and opens one image.

A `pass` or `fail` is stored on the preview record with `rendererVersion:'server-chromium/<playwright version>'`. The operation has a 25-second hard deadline; `POST /api/authoring` runs on the Node runtime with `maxDuration=60` to leave room for a cold Chromium start. `unavailable` is not a verdict about the graphic — it means the check could not run, and a human should open the fit-check link.

The browser is `playwright-core` driving `@sparticuz/chromium` on Linux (Vercel). Off Linux — a maintainer's own machine — the same `playwright-core` launches a locally installed Chrome instead: `PLAYWRIGHT_CHROMIUM_PATH` if it is set, otherwise the `chrome` channel. Both packages are `serverExternalPackages` in `next.config.ts` so the native pack is traced into the function rather than bundled.

## Server-attested fit measurement (D18, behaviour change)

Before this change, `review_draft` accepted a `browserMeasurement` **asserted by the caller**: an MCP client could claim `overflow:false` without rendering anything. It now depends on who is asking.

- **MCP actors** (the `mcp:` actors this OAuth server mints): only a stored, server-attested measurement counts — a `fit_check_draft` `pass` on that exact preview whose `rendererVersion` starts `server-chromium/`. An asserted measurement is ignored, and without the attestation the call is refused with `review_required` — "Exact-version browser fit review is required". `publish_draft` continues to refuse for the same reason.
- **The web dock** (a signed-in member measuring in their own browser) is unchanged.
- Since packet A2 the receipt records `approvedBy` (`agent` for an MCP actor) and the member, and `humanApproved` is optional input; see "One-call publish" above.

Existing agent scripts that asserted a measurement must now call `fit_check_draft` first.

## Preparing a service from centralreform.live (`prepare_service_from_setlist`)

`prepare_service_from_setlist({setlistId, name?, service?})` builds a prepared service on `/services` from a planned service on centralreform.live. Each setlist row is matched to a published graphic — by liturgy page (`{book, folio}`) where the row carries one, otherwise by the console's forgiving title search — and the result is an ordinary service collection with a coverage row per row of the setlist: *Covered*, *Needs review*, *Needs a graphic*, or *Not needed*. Rows that could not be settled come back in `unmatched` with the reason for each.

Where two published graphics share the same liturgy page, the tool never picks one: the row is *Needs review*, owned by "Unassigned", with both graphics named, and the entry holds both as alternates for a person to choose between.

**It never publishes anything, never changes a published graphic, and never puts anything on screen.** It writes exactly one thing: a new prepared service you can open and edit on `/services`.

Requires an authoring member. On a congregation without the centralreform.live credential it returns a plain refusal — `{"ok": false, "reason": "unconfigured", "message": "Importing from centralreform.live is not set up for this congregation."}` — not an error. The credential and its two variables are described in `docs/WORKSPACE-DEPLOYMENT.md`; the same import is offered on `/services` as **Import from centralreform.live**.

## Editing prepared services (S2)

A prepared service is an ordered list of **rows**. A row may hold graphics (an *entry*: one graphic, alternates, or a multipart sequence) and a coverage decision (*Covered*, *Needs review*, *Needs a graphic*, *Intentional fallback*, *Not needed*), plus an optional button label, camera hint and note. Tools address rows by `rowId` (from `get_service`); `/services` keeps showing entries and coverage, reordered to follow the rows.

| Tool | Does | Web equivalent on `/services` |
|---|---|---|
| `list_services` | Services, newest first, with row counts by readiness | the collection list |
| `get_service` | One compact line per row; `view:'full'` returns the stored record | opening a collection |
| `service_readiness` | Per row: covered / needs review / needs a graphic / not needed, with the next step | the coverage map summary |
| `list_live_setlists` | Recent centralreform.live setlists to import | Import from centralreform.live |
| `create_service` | Empty, `from:'library'`, or from `rows` in order | Start empty / Start from library |
| `rename_service` | New name or service label | editing the collection title |
| `add_entry` | Graphics as a new row at `position`, or onto a row that has none | Add graphic / as alternates / as multipart |
| `remove_entry` | Removes a row's graphics; a row with a coverage decision keeps its place | Remove on an entry |
| `reorder_entries` | Full `orderedRowIds`, or `rowId` + `toIndex` | the ↑ ↓ buttons |
| `swap_graphic` | Replaces one graphic on a row (and the matching coverage graphic) | remove + add |
| `resolve_coverage_row` | Settles a row with one graphic; rewrites its entry to that graphic | editing a Needs review item |
| `set_coverage_row` | Adds or edits a coverage decision and row details; `clear:true` removes the decision | Add / Edit / Remove coverage item |
| `set_names` / `clear_names` | The service's names list; clearing is refused while a names panel is on air | Names for this service |
| `archive_service` / `restore_service` | Archive (removes the names list; refused while on air) and restore | Archive / Restore |
| `refresh_from_setlist` | Re-imports from the stored origin; **dry run by default** | none (new) |

`refresh_from_setlist` matches rows by setlist track id. A row a person decided (covered, not needed, intentional fallback, or graphics on a row without coverage) is never changed; a row still waiting on a decision takes the new match; new setlist rows are inserted in setlist order; rows added by hand keep their place after the row they followed; rows no longer on the setlist are kept and reported unless `removeMissing:true`.

Every change takes `expectedVersion` (the version `get_service` returned) and returns the new `version`; a stale version is refused with a sentence and writes nothing. Unresolved coverage rows default their owner to "Unassigned", as the importer does. `get_service` reports `serviceRef`, the id a deck button generated from the service sends with its commands so the cue log attributes them (R-S3; the deck side is Track C). The web's `search_coverage_sources` is covered by `search_sources`, and feedback (`record_feedback`, `update_feedback`, the CSV) lives on `/services/log` and is not an MCP tool. None of these tools publishes a graphic or puts anything on screen.

## The Companion deck (C3)

Each congregation has one stored Companion deck (`companion_decks`, db/companion-decks.sql): the whole Stream Deck configuration, camera, vMix and X32 keys included, as a complete and stable library. There is no weekly service page. CRC's deck is created from its released seed the first time it is read; until C4 seeds TBI's deck from Simone's export, every TBI deck tool refuses with "The TBI deck hasn't been seeded yet…". Rows and columns count from 0, as Companion's own `page/row/column` locations do.

| Tool | Does |
|---|---|
| `get_deck` / `get_deck_page` | The deck in brief (version, pages, chains, templates, connection labels) / one page cell by cell with cues, roles, gestures, fixed keys and free cells |
| `create_page`, `rename_page`, `move_page`, `delete_page` | Pages on the deck's templates. `chainAfter` joins a service's Prev/Next chain, and `jumpFrom` adds a key that reaches the page. Prev/Next labels and jumps follow a rename or a move. |
| `place_button`, `move_button`, `remove_button` | Keys: cue, jump, module action, device key, camera merge, or `copy` of another key. A device key placed twice gets new ids. |
| `bind_cue`, `attach_camera_gesture` | Point a cue key at another cue, keeping its gesture. Add, copy or remove the camera gesture (only where the page template allows gestures). |
| `apply_template`, `layout_column` | Put back a template's fixed keys; lay out a column by the grammar |
| `sync_deck_with_catalog` | After publish, revise or retire: places new cues, relabels renamed ones, removes (or flags) keys on retired cues. **Dry run by default.** |
| `check_service_on_deck{serviceId}` | Is every graphic a prepared service needs on the deck? Says where each one is, and where each missing one would go. |
| `validate_deck` | C2's validator with the live catalog's published and retired lookups |
| `export_deck_config{scope:'full'}` | Validates, then returns a signed 15-minute download link (`/api/companion/deck?token=…`), the file's sha256 and every connection label the booth must match exactly |

**Writes.** Every change takes `expectedVersion` (the deck version from `get_deck`). It is applied to a copy and validated, then saved only if it adds no error-severity finding. Otherwise it is refused in plain sentences and nothing is saved. A stale version is refused.

**The grammar** (Michael's H1–H4). A column is a slot. A sequence runs down its column, lead at the top, and continues into the next column. Alternates of a slot share its column. A new cue's standing page is the page whose keys already hold its slot, matched by name with part numbers, parentheses and service words ignored. When several pages match, the service word in the cue's name (Friday, Saturday, Holy Days…) or the prepared service's name narrows it. `sync_deck_with_catalog` never places a cue silently when it can't tell: it lists the candidate pages and takes `placements[{cueId, page, row?, column?, label?}]`. Without `cueIds`, it considers cues published or changed since the deck was last synced. A renamed cue's label is updated only when the label came from its name; a hand-written label is flagged (`relabelHandWritten:true` overrides).

**Export.** The file is the Companion full export of the stored deck, byte for byte what `renderDeck` makes. For the unchanged CRC seed it is the preset released on 2026-09-23 (sha256 `bfc718e1…`). It holds connection labels only, never a connection's config or secrets. The link names the deck version and the sha256 of the validated bytes, so it is refused (410) once the deck changes. Signing uses `COMPANION_EXPORT_KEY` when it is set (32+ characters). Otherwise it uses a key derived, with a purpose label, from `RELAY_SECRET` or `CONTROL_KEY`, never the secret itself. The Setup page lists the same download for a signed-in member who runs the booth (`/api/companion/deck?download=full` validates, then redirects to a fresh link).

## Converting a Singular deck (C4)

Two tools take a Stream Deck that still fires Singular.live to one that fires the congregation's Overlays module. Both are TBI's today (Simone's deck); CRC's deck is built from its released preset and is changed with the deck tools.

| Tool | Does |
|---|---|
| `seed_deck_from_export` | Stores the workspace's deck from a Companion 5 full export (`export`, the `.companionconfig` base64-encoded, at most about 700 KB per request) or from Simone's committed 14 September seed (`useCommittedSeed:true`). Every page, position, label and colour is kept; Companion's built-in page up / number / down buttons stay; camera and OBS buttons are carried as device fragments; each Singular graphic button becomes an inert placeholder that records what it fired. Singular connections are dropped and a `TBI_Overlays` connection is added. **Dry run by default**; replacing a stored deck needs `expectedVersion`. |
| `convert_singular_deck` | Matches each placeholder's composition to a published graphic with the title search `prepare_service_from_setlist` uses (same thresholds), plus the button's own label as a second query that can only ever propose candidates. Rows come back *Covered*, *Needs review* or *Needs a graphic*, with defects named: `in-out-mismatch`, `label-names-other-prayer`, `duplicate-label`, `working-note-label`, `composition-missing` (when the Singular compositions are known) and the non-blocking `duplicate-button` / `same-graphic-different-labels`. A matched row with a blocking defect is Needs review. **Dry run by default**; with `dryRun:false`, `expectedVersion` and `bind` (row ids from the dry run), only Covered rows are bound, as one-press toggle keys with the Requested and Rendered lights and her colours; naming any other row refuses the whole call. `deck:'committed-seed'` previews the committed seed without storing it. |

Connection `config` and `secrets` are discarded on the server before anything is kept (stubs copy only id, label, module, version, sort order, update policy and upgrade index), the uploaded file is never stored, and a carried button naming a password, secret or token is refused. Row ids are `page/row/column` counted from 0, as Companion writes button locations. Both tools write to the deck tools' own store (C3, `companion_decks`), so a seeded or converted deck is the one `get_deck` reads; until db/companion-decks.sql is applied, writes are refused with a sentence. The plain-language report for Daniel and Simone is regenerated with `node scripts/convert-companion-singular.mjs --tbi-report` ([TBI-CONVERSION-REPORT.md](planning/2026-09-23-mcp-gap-analysis/TBI-CONVERSION-REPORT.md)); `--tbi-seed <export>` re-derives `lib/companion-deck/tbi-seed-data.json`.

### Singular reference material and content matching (T3)

**`import_singular_extract{workspace, extract | importId, dryRun?, expectedVersion?}`** stores what each old Singular composition showed, so every conversion row can show the old text beside the proposed graphic. `extract` is the shape the first conversion pass pulled from Singular's control model (see `Claude outputs/singular-extract-summary.md`), taken strictly: `{apps:[{label, name?, id?, subcompositions:[{id, name, parentApp?, template?, layer, fields:{<fieldId>:{title?, type?, value?}}, notes?, imageAssetId?}]}], extractedAt?}`. `label` is the Companion connection label that fires the app (`kab`, `morn`, `singular__HHDs`). Only **app, name, layer and text** are stored per composition: the text is the `title`, `titleAccent` (or `accentText`) and `text` field values, one per line, with Singular's spacing hacks and bidi controls tidied and the wording untouched. `imageAssetId` (an asset from `upload_asset`) is an optional picture of the old slide. Fields, templates, notes and any link are dropped. **Anything that looks like a credential** anywhere in the input (a Singular control link `…/apiv1/control/…`, a key named like a token, password, secret, API key, cookie or session id, a `Bearer` value, a `?token=` query) is refused with a sentence that names where it is, without repeating it, and nothing is stored. Apps in the call replace stored apps of the same label; other apps are kept. **From a dropped file (G1):** pass `importId` (a ready `singular-extract` import from `open_import_dropzone`) instead of `extract`; exactly one of the two is required, the file is checked for credentials again, and the result adds `from{importId, sha256, bytes}`. **The flat shape** the recovered 24 September TBI extract uses is read too: `{source?, extractedAt?, apps?:[{label, rootName?, compositionRefId?, topLevelSubs?}], subcompositions:[{id, name, parentApp, path?, layer, fieldSignature?, fields:{<fieldId>:{index?, title?, type?, value?}}}]}`. It is grouped by `parentApp` (in `apps[]` order, `rootName` as the app name) into the nested shape, dropping `path`, `fieldSignature` and field `index`, and then meets the same limits as the inline shape (12 apps, 600 compositions per app). Every result reports `shape` and the `total` of compositions. **Dry run by default**; once material is stored, a write needs its `expectedVersion`. Storage: `singular_references` (`db/singular-references.sql`, not applied; in memory under local rehearsal); until the table exists the tool says so.

**On `convert_singular_deck`** every row now carries `reference{origin:'singular', app, comp, text, imageAssetId?}`: what the button's first press showed. Before an extract is imported `text` is empty and the result's `references.note` says so; compact rows show `oldText` (160 characters), `view:'full'` the whole reference. With material stored:

- matching compares **content first**, then the title search: a composition's text is scored against every published graphic's texts, and the row is Covered when the best graphic is EXACT or TEXT-MATCH and no other is nearly as strong (within 0.05); SAME-PRAYER-DIFFERENT-SPLIT and PARTIAL graphics become candidates for review. The reason says "by what it shows" when content decided it;
- a button firing a composition that no longer exists **in an imported app** gets `composition-missing` (apps not imported are not judged).

Pass a row's `reference` to **`create_draft{…, reference}`** and the draft keeps it (through edits too; it is never part of the cue or its hash). A review board (T4) shows a draft's reference under *Before* without it being passed again.

**The matcher** (lib/companion-deck/singular-match.ts) re-implements the first pass's written method (work/companion-simone/crc-match-report.md): Hebrew NFKD (Singular stores presentation forms U+FB1D–FB4F), U+0591–U+05C7 stripped, final letters folded, compared as word sets and by sequence; transliteration lower-cased, de-accented, apostrophes dropped, ch/kh→h, tz/ts→z, doubled letters collapsed; names with a liturgical-spelling table (Aleicheim≡Aleichem, Veehavta≡V'ahavta, Readers≡Chatzi Kaddish, Keddusha≡Kedusha, …), sequence ratio, word-set Jaccard and a consonant skeleton, with trailing part numbers split off; containment as the share of the smaller side's words found in the larger. **This is not a rerun of the first pass on its inputs**: its script and its `singular-extract.json` did not survive. What is checked is its category rules: `classifyMatch` reproduces all 540 categories the first pass recorded from its recorded sub-scores (tests/singular-match.test.ts over tests/fixtures/singular-first-pass-categories.json, names, categories and numbers only), so its counts too: EXACT 34 and TEXT-MATCH 27 of the 207 Companion-referenced compositions, 107 and 66 of all 540. The normalisation is checked on hand-built Hebrew and transliteration. The scores themselves (and so which graphic ranks first) may differ from the first pass's on the same text.

## Applying a deck plan in one call (G6)

**`apply_deck_plan{workspace, importId | rows, expectedVersion?, dryRun?, targets?}`** lays a whole deck plan on the stored deck in one write, instead of a few hundred `place_button` / `bind_cue` calls. A plan is one row per button with the columns of the TBI build's `deck-plan.csv`: `page,row,col,label,bg,targetKind,targetKey,panelIndex,notes` (and an optional `pageName`). Give it as `rows` (objects with those columns, up to 400) or as the `importId` of a `deck-plan` import (`open_import_dropzone`), which may be the CSV itself (quoted fields, commas and line breaks inside quotes) or a JSON array of the same rows. Rows and columns count from 0.

| targetKind | What happens to the cell |
|---|---|
| `local`, `corpus`, `slide`, `crc` | A graphic. `targetKey` is the build key its graphic was made under: a `draft` key (`batch_create_drafts`), else a `draft-set` key, where `panelIndex` (0-based, default 0) picks the part. The draft must be published; the cell becomes a one-step cue key on that cue with the plan's `label` and `bg` (`#rrggbb`), and the Requested and Rendered lights every cue key carries. A cue key already there keeps its ids (and any camera gesture); an unconverted Singular placeholder is replaced. `targets` (key → cue id, or key → [cue ids by panel]) overrides or extends the build keys. |
| `birddog`, `obs` | The camera or OBS scene key already on the deck at that cell is kept exactly as it is; it is never rebuilt from the plan, and no device action or connection setting is ever written. When the deck does not have that key there (`targetKey` names its actions, `Birddog:pt:up_left; Birddog:pt:stop`), the finding says where it is, or that it is missing. |
| `empty` | The cell ends empty: a graphic key there is removed. A device, navigation or template key is kept and reported. |
| `dropped` | Not placed, and reported. A graphic key left on its cell is removed with it, unless another row uses the cell. |

Companion's built-in page up / number / down and every template key are never touched; a graphic row on one is refused. A page the plan names that the deck lacks is created on the deck's `service` template with its fixed keys; existing pages keep their names unless a row gives `pageName`. Text colour is kept when the background is unchanged, otherwise black or white, whichever reads. A background equal to the palette's Requested, Rendered or disconnected colour is reported (that light would not show), not refused.

**Refusals.** Any graphic row whose key is unbuilt, unpublished, retired, or has no part at its `panelIndex`, a colour that is not `#rrggbb`, a label over 40 characters, two rows claiming one cell, or a graphic on a device or navigation key is a **blocking** finding naming the row (page, row, column, label, key): the apply is refused and nothing is written. **Dry run by default**: it writes nothing and returns every change (`placed`, `rebound`, `emptied`, `dropped`), the counts (placed, rebound, unchanged, device keys kept, emptied, dropped, findings, blocking, pages created), every finding, graphic keys on the deck no row names (`notInPlan`, kept), and `validate_deck`'s findings on the would-be deck. With `dryRun:false` and `expectedVersion` the plan is saved in one write, validated like every deck change (a stale version is refused, and so is a change that adds a validator error), and the result adds the new version and the validator's result.

## Client status

The routes implement the standards used by remote MCP clients, including protected-resource discovery, authorization-server discovery, dynamic public-client registration, PKCE, bearer challenges, refresh, and revocation. The automated smoke test exercises Streamable HTTP initialization, tool discovery, tool invocation, input boundaries, audience/scope constraints, redirects, PKCE, and chunked body limits. A real ChatGPT or Claude connection still requires deployment and provider-side testing; this repository does not claim that either client has been connected.

## Reading what a service did (`get_service_history`)

`get_service_history({since, until, after, limit})` reads this workspace's cue log: one row per
accepted live command, with the graphic's id, its liturgical position (`unitId`, `momentId`,
`book`, `folio`), the time, where the command came from (`control`, `companion` or `mcp`; the
console's own WebMCP tools send `mcp`), the prepared service when one is known, and the command's
`commandId` (ruling 10: the caller's correlation id, `null` on rows recorded before the relay kept
it), so an agent can find the row its own command wrote. It is bounded to the last 2,000 commands or 14 days, whichever is smaller, and pages by
`seq`.

It is read-only in the strongest sense: it puts nothing on screen, changes nothing, and carries no
graphic names, no text and nobody's identity. Without the live relay it answers
`{ok:false, reason:"unavailable"}` rather than failing, because the legacy path keeps no history.

## Live control (packet V3)

Nine tools act on (or read) this workspace's live output. They need the `crc.live` scope (an authoring-only token is refused with `insufficient_scope: needs crc.live`; a live-only token can use them and still can't author), and they go through the same command core as `POST /api/command` (`lib/live-command.ts`), so every press lands in the cue log as `source:'mcp'` with its `commandId`. Registration: `lib/mcp/live.ts`; `lib/mcp.ts` sends the live group to a separate live operation, wired in `app/api/mcp/route.ts` to `runMcpCommand` and the same snapshot and catalog `GET /api/state` and the output read.

Every live tool takes `target`, which must be `'live'`. `'rehearsal'` is refused in words with nothing sent: there is one relay room per workspace, and a separate rehearsal output is a later plan (decision 3). The write tools also take the required `workspace` and optional `commandId` (8-80 letters, digits, `-`, `_`; retrying with the same id replays the first answer instead of pressing twice), `serviceId` (a prepared service UUID, stored as the row's `serviceRef`), `ifRevision` (the relay refuses, changing nothing, if the state has moved on), `override` and `reason`.

| Tool | Relay action | What it does |
| --- | --- | --- |
| `get_live_state` | read | Revision, the requested graphic, whether a graphics browser has acknowledged it (`rendered`: `rendered` / `in transition` / `error` / `not acknowledged`, and an `onScreen` sentence built only from acks), scan card, resting-logo preference, `lastPress` per class (`companion`, `console`, `agent`), connected controllers, and the deck guard. |
| `show_graphic{cueId}` | `in` | Shows a published graphic with its In animation. An id not in the live catalog, or a hidden alias, is refused before sending. |
| `take_out{cueId}` | `out` + `ifCue` | Animates that graphic off only if it is the one on screen; otherwise refused with nothing sent. Scan card and logo untouched. |
| `animate_out` | `clear` | Animates whatever is on screen off. Scan card and resting-logo preference untouched. |
| `clear_now{immediate:true}` | `cut` | Clears at once with no animation. As the relay does today (`nextState` for `cut`), this also removes the scan card and turns the resting-logo preference off, which stays off until someone turns it on; the result says so and returns `alsoCleared`. Without `immediate:true` the schema refuses it. |
| `next_panel` / `previous_panel` | `in` + `ifCue` | Works out the neighbour of the live graphic in its `— NN of MM` set on the server (`lib/panel-navigation.ts`, a port of the Companion module's `panelTarget`, held equal to it by a test), wrapping at either end, never leaving the set's id namespace and never landing on a hidden cue. `ifCue` makes it relative to what was read. Refused with nothing sent when nothing is live or the live graphic is not in a set. |
| `set_scan_card{on, page?}` | `bug` | On without `page` keeps the current page; `page:null` clears it. |
| `set_resting_logo{on}` | `logo` | Sets the preference. The result reports the preference (`restingLogoPreference`, `visibility:'not reported'`) and never claims the mark is on screen: the output hides it under any graphic or the scan card. |

After an accepted press each write tool polls the live state for up to about 3 seconds and reports `renderer` as it is: `acknowledged:true` when a graphics browser settled on the revision the relay answered, otherwise `not yet`, `in transition`, `error`, `overtaken` (something else changed the output first) or `superseded`. A replayed `commandId` says it was replayed. Relay refusals (a failed `ifRevision`/`ifCue`, an unknown cue, a malformed page) come back as the relay's sentence with `isError`.

**Deck guard (decision 4).** While any Companion deck pressed a button within the guard window, every live write tool is refused with a sentence naming how long ago the deck pressed, unless the call passes `override:true` with a `reason` (an override without a reason is refused). The window is measured on the relay's clock from V1's `lastPress.companion`, which counts applied and superseded presses. It is workspace configuration: `WORKSPACE_DECK_GUARD_MINUTES`, a whole number from 1 to 240, default 5 (`lib/workspace.ts` `deckGuardMinutes`); there is deliberately no value that turns it off, and an invalid value holds live control back. A live service that does not report press times (a relay older than V1, or the legacy Postgres path) cannot be judged, so the guard treats it as active: refused unless overridden. The cue log has no note field (`relay/src/protocol.ts` `HISTORY_KEYS`), so an override's reason is recorded in the tool result (`override`) and one server log line, `{"event":"mcp_live_override", workspace, tool, commandId, reason, guardActive, lastCompanionPressAt}`, matched to the cue-log row by `commandId`. The guard reads state and then sends, so a deck press in the gap between the two is not caught; `ifRevision` closes that gap for a caller that wants it.

**On the deck.** The Companion module shows agent activity: the variable `$(<label>:last_source)` reads `Agent`, `Companion` or `Console` for whoever made the newest press the relay recorded (blank until a web and relay that report `lastPress` are live), and the boolean feedback **Last command came from an agent** (`last_source_agent`) lights while it is `Agent`. The realtime snapshot never says who changed it, so the module takes `lastPress` from its own command answers and, after a revision it did not make, from `GET /api/state` (one read at a time; a failed read keeps the last value and changes no status). No preset uses them yet (C5).

Release order: the relay with V1 ships first (docs/RELAY-RELEASE.md); these tools work against an older relay but the guard then refuses without an override, and the Companion variable stays blank. The module change reaches decks only in the next packaged module version.
